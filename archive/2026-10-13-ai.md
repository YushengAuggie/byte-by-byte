### 为什么 LLM 推理慢的根源：Prefill vs Decode

LLM 推理有两个截然不同的阶段：
- **Prefill (预填):** 一次性处理整个 prompt — **计算密集 (compute-bound)**，GPU 跑满。
- **Decode (生成):** 一次吐一个 token — **内存带宽密集 (memory-bound)**，GPU 大部分时间在搬 weights。

Prefill is **compute-bound** (GPU math units saturated). Decode is **memory-bound** (GPU idling, DRAM thrashing). KV cache is the single most important optimization for decode.

**没有 KV 缓存**：生成第 N 个 token 要重新算前 N-1 个 token 的 attention — 复杂度 **O(N²)** 累计。
**有 KV 缓存**：每个 token 的 K、V 向量算一次，存起来，后续 token 直接查 — 复杂度 **O(N)** 累计，但内存吃紧。

Without KV cache: regenerating K,V for every prior token → O(N²) cumulative. With cache: compute once, reuse → O(N) time, but memory explodes.

---

### KV 缓存到底存什么？

每层 attention 有 Q (query), K (key), V (value) 三个矩阵。生成第 t 个 token 时：
- `Q_t` 要用当前 token 的 hidden state 新算一个。
- `K`, `V` 需要**前面所有 token 的** — 这些是不变的历史，缓存起来。

每层 KV cache 的大小 **= `2 × batch × seq_len × num_heads × head_dim × bytes_per_elem`**。

Llama-3-8B 举例 (32 layers, 8 KV heads, 128 head_dim, fp16)：
```
每 token 每层 = 2 × 1 × 1 × 8 × 128 × 2 bytes = 4 KB
全层每 token  = 4 KB × 32 = 128 KB
8K context    = 128 KB × 8192 ≈ 1 GB per request
```

**这就是为什么 LLM 服务要用 PagedAttention (vLLM) / FlashAttention** — KV 缓存的内存管理决定了吞吐量。

### 一个最小的 KV-cache 实现 (可运行)

```python
# save as kv_cache_demo.py
import torch, time
import torch.nn.functional as F

torch.manual_seed(0)
D, H, HEAD_DIM = 128, 4, 32  # model dim, heads, head dim
assert D == H * HEAD_DIM

# One attention layer's K,V projections (toy)
Wq = torch.randn(D, D); Wk = torch.randn(D, D); Wv = torch.randn(D, D)

def attention_naive(tokens: torch.Tensor) -> torch.Tensor:
    """Recompute full attention every step — the slow way."""
    # tokens: [T, D]
    Q = (tokens @ Wq).view(-1, H, HEAD_DIM).transpose(0, 1)  # [H,T,d]
    K = (tokens @ Wk).view(-1, H, HEAD_DIM).transpose(0, 1)
    V = (tokens @ Wv).view(-1, H, HEAD_DIM).transpose(0, 1)
    scores = Q @ K.transpose(-2, -1) / HEAD_DIM**0.5
    mask = torch.triu(torch.ones_like(scores), diagonal=1).bool()
    scores = scores.masked_fill(mask, float("-inf"))
    return (F.softmax(scores, dim=-1) @ V).transpose(0, 1).reshape(-1, D)[-1]

class KVCache:
    def __init__(self): self.K = None; self.V = None
    def step(self, token_vec: torch.Tensor) -> torch.Tensor:
        q = (token_vec @ Wq).view(H, HEAD_DIM)            # [H, d]
        k = (token_vec @ Wk).view(H, HEAD_DIM)
        v = (token_vec @ Wv).view(H, HEAD_DIM)
        self.K = k.unsqueeze(1) if self.K is None else torch.cat([self.K, k.unsqueeze(1)], dim=1)
        self.V = v.unsqueeze(1) if self.V is None else torch.cat([self.V, v.unsqueeze(1)], dim=1)
        scores = (q.unsqueeze(1) @ self.K.transpose(-2, -1)).squeeze(1) / HEAD_DIM**0.5  # [H,T]
        return (F.softmax(scores, dim=-1).unsqueeze(1) @ self.V).squeeze(1).reshape(-1)

# Bench: generate 200 tokens
seq = [torch.randn(D) for _ in range(200)]

t0 = time.perf_counter()
for i in range(1, 201):
    _ = attention_naive(torch.stack(seq[:i]))
print(f"naive  O(N^2): {time.perf_counter()-t0:.3f}s")

t0 = time.perf_counter()
cache = KVCache()
for tok in seq:
    _ = cache.step(tok)
print(f"kv-cache O(N): {time.perf_counter()-t0:.3f}s")
```

典型输出：
```
naive  O(N^2): 0.42s
kv-cache O(N): 0.05s   ← ~8-10x faster at seq_len=200, gap grows with length
```

### 现实中的 KV-cache 优化栈

| 技术 | 解决什么 | 代表项目 |
|---|---|---|
| **PagedAttention** | KV 碎片化、fragmentation | vLLM |
| **GQA / MQA** (Grouped/Multi-Query) | KV heads 共享减内存 | Llama 3, Mistral |
| **Sliding Window Attention** | 长 context 砍掉太老的 token | Mistral |
| **KV Quantization (int8/int4)** | 把 fp16 → int8 砍 2-4x 内存 | TGI, vLLM |
| **Prefix Caching** | 共享的 system prompt 只算一次 | vLLM, SGLang |
| **Speculative Decoding** | 小模型猜，大模型验证 — 跳步 | Medusa, EAGLE |

**生产提示：** 服务 LLM 不要自己写 attention — 直接用 vLLM/SGLang/TGI。它们在 KV 管理上 2-3 年领先手搓。你的工作是**理解它们的行为**（调 `--kv-cache-dtype`, `--enable-prefix-caching`）而不是重实现。
