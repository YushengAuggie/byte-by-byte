## 什么是上下文窗口 / What Is a Context Window?

上下文窗口是 LLM 的"工作记忆"——它能同时"看到"多少 token（大概一个英文单词 ≈ 1.3 tokens）。

A context window is the LLM's "working memory" — how many tokens it can "see" at once (roughly 1.3 tokens per English word).

```
2023 早期 / Early 2023:   GPT-3.5 = 4K tokens  (~3,000 words)
2024:                     GPT-4o  = 128K tokens (~96,000 words)
2025:                     Claude 3 Opus/Sonnet = 200K tokens
                          Gemini 1.5 Pro = 1M tokens (~750,000 words)
```

1M tokens ≈ 整本《哈利·波特》全集 × 2 — 几乎可以把整个代码库喂给模型。

*1M tokens ≈ 2x the entire Harry Potter series — you can feed an entire codebase to the model.*

---

## 为什么"更大的上下文"不是万能药 / Why Bigger Isn't Always Better

### 1. 成本与速度 / Cost & Speed

输入 token 的数量直接影响推理成本（按 token 计费）：

Input token count directly drives inference cost (pay per token):

```
GPT-4o: ~$2.50 per 1M input tokens
Claude Sonnet: ~$3 per 1M input tokens

1M token prompt × 每天100次请求 = $250/day just for inputs
```

### 2. "迷失在中间"问题 / "Lost in the Middle" Problem

研究发现，LLM 对**开头和结尾**的内容注意力最高，对**中间**的内容容易遗漏。

Research shows LLMs pay the most attention to the **beginning and end** of context; content in the **middle** is often missed.

```
Attention weight distribution (approximate):
████████░░░░░░░░░░░░░░░░████████
^start high^   ^middle low^  ^end high^
```

### 3. 延迟 / Latency

即使有 1M token 的上下文，处理全部内容的延迟比处理 10K token 的上下文高几十倍。

Even with 1M token context, processing it all takes 10-50x longer than a 10K context.

## 实用策略 / Practical Strategies

### 策略 1：RAG（检索增强生成）
不把所有文档塞进上下文，而是先检索最相关的段落。

Instead of stuffing all docs into context, retrieve only the most relevant chunks.

```
Query → Embedding → Vector Search → Top-K chunks → LLM
                                     (只传最相关的部分)
```

**适合 / Good for:** 大型私有知识库、文档问答、企业 AI

### 策略 2：分块 + 重排 / Chunking + Reranking

```python
# RAG pipeline sketch
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=200,  # 20% overlap prevents boundary cutoffs
)
chunks = splitter.split_text(document)

# embed chunks → store in vector DB
# at query time: retrieve top-K → rerank → pass to LLM
```

最佳实践：重叠率 10-20%，避免在语义边界切断内容。

*Best practice: 10-20% overlap prevents cutting off context at boundaries.*

### 策略 3：提示压缩 / Prompt Compression

用更小的模型先压缩输入，再传给大模型（LLMLingua 等技术）。

Use a smaller model to compress the input first before sending to the big model.

```
Long doc (10K tokens) → Compressor → Key sentences (2K tokens) → LLM
                                      (80% cost reduction!)
```

### 策略 4：放置顺序很重要 / Position Matters

由于"迷失在中间"效应，把最重要的内容放在**开头或结尾**：

Due to lost-in-the-middle, put the most critical content at the **beginning or end**:

```
✅ Good: [System prompt] + [Retrieved context] + [User query]
❌ Bad:  [Long doc start] + [Critical instruction buried in middle] + [Long doc end]
```

## 什么时候用长上下文 vs. RAG / Long Context vs. RAG

| 场景 / Scenario | 推荐 / Recommendation |
|---|---|
| 小文档，需要整体理解 | 直接传入上下文 |
| 大型私有知识库 | RAG |
| 代码库分析 | 长上下文（如 Gemini 1M）|
| 实时低延迟应用 | RAG + 小上下文 |
| 成本敏感场景 | RAG 压缩输入 |

## 可运行代码 / Runnable Python

```python
# pip install tiktoken
import tiktoken

def count_tokens(text: str, model: str = "gpt-4o") -> int:
    """Count tokens for a given text and model."""
    enc = tiktoken.encoding_for_model(model)
    return len(enc.encode(text))

def estimate_cost(text: str, price_per_million: float = 2.50) -> float:
    """Estimate input cost in USD."""
    tokens = count_tokens(text)
    return tokens / 1_000_000 * price_per_million

sample = "The quick brown fox jumps over the lazy dog. " * 1000
print(f"Tokens: {count_tokens(sample):,}")
print(f"Estimated cost: ${estimate_cost(sample):.4f}")
# Output: Tokens: 9,000  |  Estimated cost: $0.0225
```

## 🧒 ELI5

上下文窗口就像你的桌子——桌子越大，能放的书越多。现在 AI 的桌子已经大到可以放整个图书馆了。但问题是：桌子越大越贵，而且东西太多你也容易忽略中间的那本书。所以聪明的做法是：先用"图书管理员"（RAG）帮你找到最相关的几本书，再放到桌子上，又快又省钱。

*A context window is like your desk — the bigger it is, the more books you can put on it. Today's AI desks can fit an entire library! But bigger desks cost more, and you're likely to miss the book in the middle of a huge pile. The smart move: use a "librarian" (RAG) to fetch only the relevant books first, then put just those on your desk. Faster and cheaper.*
