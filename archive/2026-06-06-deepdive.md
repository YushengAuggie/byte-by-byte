## Overview / 概述

**为什么这个话题值得花 18 分钟？**

你每次在 Google Docs 里和同事同时编辑一个文档，背后都有一套精妙的算法在保证大家看到的内容一致。这套算法不是锁（太慢），不是"最后写入者赢"（数据丢失），而是一种叫做**操作变换（Operational Transformation, OT）**或**无冲突复制数据类型（CRDT）**的技术。

这两者是协同编辑领域的核心技术，也是系统设计面试里**拉开差距的关键知识点**。大多数候选人能画出 WebSocket + 后端 + 数据库的架构图，但极少有人能解释冲突是怎么解决的。

**Why this topic is worth 18 minutes:**

When you and a colleague edit a Google Doc simultaneously, a sophisticated algorithm silently resolves conflicts in real time. It's not a lock (too slow), not "last write wins" (data loss), but rather **Operational Transformation (OT)** or **Conflict-free Replicated Data Types (CRDTs)**. These are what separate good system design answers from great ones.

## Part 1: Theory / 理论基础 (5 min)

### 核心问题：并发冲突

想象两个用户同时编辑同一个文档，初始内容是 `"abc"`：

```
User A: 在位置 0 插入 "X"  → "Xabc"
User B: 在位置 2 删除 'c'   → "ab"

如果 A 先到达服务器，B 的操作应该作用于哪个状态？
- 如果直接在 "Xabc" 上删除位置 2 → 删掉了 'b'  ❌
- 正确答案：删除位置 3（因为 A 的插入使原来的 c 向右移了一位）✓
```

这就是 **OT（操作变换）**要解决的问题：**如何调整一个操作，使它在另一个并发操作已经执行之后仍然能产生正确的结果。**

### The Core Problem: Concurrent Conflicts

```
Initial: "abc"
User A: insert("X", pos=0) → "Xabc"
User B: delete(pos=2, char='c') → "ab"

Server receives A first, then must apply B.
B was generated against "abc" where 'c' was at index 2.
In "Xabc", 'c' is now at index 3.
OT must transform B: delete(pos=2) → delete(pos=3)
```

### 两种解法对比 / Two Approaches

| 维度 | OT (Operational Transformation) | CRDT |
|------|----------------------------------|------|
| 历史 | 1989年，Google Docs 用的 | 2006年起，Figma、Notion、Linear 转向 |
| 核心思路 | 在服务器端变换操作序列 | 数据结构本身保证收敛 |
| 需要中心服务器 | **是**（操作变换逻辑集中在服务端） | **否**（P2P 可用，离线优先） |
| 实现复杂度 | 高（OT correctness 很难证明） | 中高（不同 CRDT 类型不同） |
| 代表产品 | Google Docs, Etherpad | Figma, Apple Notes, Automerge |

### OT 的两个核心性质 / OT's Two Core Properties

```
设 op1 和 op2 是两个并发操作，T 是变换函数：

Inclusion Transformation (IT):
  apply(apply(doc, op1), T(op2, op1)) == apply(apply(doc, op2), T(op1, op2))
  → 无论哪个操作先到，最终结果相同 ✓

Exclusion Transformation (ET):
  undo 操作时用到，撤销已经被其他操作变换过的操作
  → 实现 Ctrl+Z 在协同场景下的正确行为
```

### CRDT 的核心思想 / CRDT Core Idea

CRDT 不是变换操作，而是**设计一种特殊的数据结构，使得任意顺序的合并都能产生相同结果**。

**关键性质（Semilattice）：**
- 结合律：`merge(a, merge(b, c)) = merge(merge(a, b), c)`
- 交换律：`merge(a, b) = merge(b, a)`  
- 幂等性：`merge(a, a) = a`

满足这三条，就能保证最终一致性，不需要中心协调者。

CRDT doesn't transform operations — it **designs data structures where any order of merges produces the same result**. The three laws above guarantee eventual consistency without any central coordinator.

## Part 2: Step-by-Step Implementation / 一步一步实现 (8 min)

### 方案一：OT 实现文本协同 / OT Implementation

```python
from dataclasses import dataclass
from enum import Enum
from typing import Optional

class OpType(Enum):
    INSERT = "insert"
    DELETE = "delete"
    RETAIN = "retain"  # skip N characters unchanged

@dataclass
class Operation:
    """
    Represents a single atomic edit operation.
    Uses the 'retain/insert/delete' triple common in OT libraries (like OT.js / ShareDB).
    """
    type: OpType
    pos: int          # position in the ORIGINAL document (before this op)
    char: Optional[str] = None  # only for INSERT
    length: int = 1   # for DELETE or RETAIN


def transform(op_a: Operation, op_b: Operation, priority: str = "left") -> Operation:
    """
    Transform op_a against op_b.
    priority="left" means op_a wins on tie (same position insert).
    
    This implements the INSERT/DELETE x INSERT/DELETE matrix.
    """
    if op_a.type == OpType.INSERT and op_b.type == OpType.INSERT:
        # Both insert at same position: priority breaks tie
        if op_b.pos < op_a.pos or (op_b.pos == op_a.pos and priority == "right"):
            # op_b inserts before (or at same pos with lower priority)
            # → op_a's position shifts right by 1
            return Operation(OpType.INSERT, op_a.pos + 1, op_a.char)
        return op_a  # op_b is at or after op_a, no shift needed

    elif op_a.type == OpType.INSERT and op_b.type == OpType.DELETE:
        if op_b.pos < op_a.pos:
            # op_b deleted something before our insert position
            # → our position shifts left by 1
            return Operation(OpType.INSERT, op_a.pos - 1, op_a.char)
        return op_a  # deletion was at or after our position, no shift

    elif op_a.type == OpType.DELETE and op_b.type == OpType.INSERT:
        if op_b.pos <= op_a.pos:
            # op_b inserted before our deletion target
            # → our target shifts right by 1
            return Operation(OpType.DELETE, op_a.pos + 1)
        return op_a

    elif op_a.type == OpType.DELETE and op_b.type == OpType.DELETE:
        if op_b.pos < op_a.pos:
            # op_b deleted something before our target → shift left
            return Operation(OpType.DELETE, op_a.pos - 1)
        elif op_b.pos == op_a.pos:
            # Both deleting the same character! op_a becomes a no-op.
            # We return a RETAIN(0) to signal "already done"
            return Operation(OpType.RETAIN, op_a.pos, length=0)
        return op_a


class OTDocument:
    """
    Simple OT-based collaborative document (server-side coordinator).
    """
    def __init__(self):
        self.text = ""
        self.history: list[Operation] = []  # all committed ops in order

    def apply(self, op: Operation) -> str:
        """Apply an operation to the document text."""
        if op.type == OpType.INSERT:
            self.text = self.text[:op.pos] + op.char + self.text[op.pos:]
        elif op.type == OpType.DELETE:
            if op.length > 0:  # skip no-op deletes
                self.text = self.text[:op.pos] + self.text[op.pos + 1:]
        return self.text

    def receive(self, op: Operation, client_version: int) -> Operation:
        """
        Server receives an op from a client.
        client_version = how many ops the client has seen (its 'parent' revision).
        
        We must transform op against all ops since client_version.
        """
        # Transform op against every concurrent op the client hasn't seen yet
        concurrent_ops = self.history[client_version:]
        transformed_op = op
        for server_op in concurrent_ops:
            transformed_op = transform(transformed_op, server_op)
        
        self.apply(transformed_op)
        self.history.append(transformed_op)
        return transformed_op  # broadcast this to all other clients


# ─── Demo: The classic conflict scenario ───────────────────────────────────────
doc = OTDocument()
doc.text = "abc"
doc.history = []

# User A: insert "X" at position 0
op_a = Operation(OpType.INSERT, pos=0, char="X")

# User B: delete 'c' at position 2
op_b = Operation(OpType.DELETE, pos=2)

# A's op arrives first at version 0 → applied directly
doc.receive(op_a, client_version=0)
print(f"After A: '{doc.text}'")  # "Xabc"

# B's op arrives (still thinks it's at version 0, before A)
# server transforms B against A's insert
doc.receive(op_b, client_version=0)
print(f"After B: '{doc.text}'")  # "Xab" ← 'c' correctly deleted ✓
```

### 方案二：CRDT 实现 — Logoot / RGA 思路 / CRDT Approach

```python
import uuid
from dataclasses import dataclass, field
from typing import Optional

@dataclass(order=True)
class Identifier:
    """
    Every character in a CRDT document gets a globally unique, 
    totally-ordered identifier. No two identifiers are equal.
    
    This is the key insight: positions become stable IDs, not integers.
    When A inserts between IDs 10 and 20, it picks ID 15.
    No matter what B does concurrently, character 15 stays where it is.
    """
    pos: float       # fractional position for ordering (Logoot-style)
    site_id: str     # which client created this (for tiebreaking)
    counter: int     # lamport clock to ensure uniqueness
    
    def __eq__(self, other):
        return self.pos == other.pos and self.site_id == other.site_id


@dataclass
class CRDTChar:
    """A single character in the CRDT sequence."""
    id: Identifier
    char: str
    deleted: bool = False  # tombstone — deleted chars stay in the structure


class RGADocument:
    """
    Replicated Growable Array (RGA) — a popular CRDT for text.
    
    Key properties:
    - Each char has a unique ID (site_id + lamport clock)
    - Causality: an insert references its left neighbor's ID
    - Delete = tombstone (never physically remove, just mark)
    - Merge: union of all char sets, order by ID
    """
    def __init__(self, site_id: str):
        self.site_id = site_id
        self.clock = 0
        # chars sorted by their stable IDs
        self._chars: list[CRDTChar] = []

    def _new_id(self, left_pos: float, right_pos: float) -> Identifier:
        """
        Generate a new identifier that falls between left and right positions.
        Uses fractional indexing — the classic "pick a number between 10 and 20".
        """
        self.clock += 1
        mid_pos = (left_pos + right_pos) / 2
        return Identifier(pos=mid_pos, site_id=self.site_id, counter=self.clock)

    def local_insert(self, char: str, after_index: int) -> CRDTChar:
        """
        Insert a character after the visible character at after_index.
        Returns the new CRDTChar (to be broadcast to peers).
        """
        # Find the fractional position boundaries
        left_pos = self._chars[after_index].id.pos if after_index >= 0 else 0.0
        right_pos = (
            self._chars[after_index + 1].id.pos 
            if after_index + 1 < len(self._chars) 
            else 1.0
        )
        new_id = self._new_id(left_pos, right_pos)
        new_char = CRDTChar(id=new_id, char=char)
        
        # Insert in sorted position
        insert_at = after_index + 1
        self._chars.insert(insert_at, new_char)
        return new_char

    def local_delete(self, index: int) -> CRDTChar:
        """
        Delete the visible character at index.
        Tombstone only — the char stays in _chars forever.
        """
        # Find the nth visible (non-deleted) char
        count = 0
        for c in self._chars:
            if not c.deleted:
                if count == index:
                    c.deleted = True
                    return c  # broadcast this tombstone
                count += 1
        raise IndexError("No visible character at that index")

    def apply_remote(self, op: CRDTChar):
        """
        Merge a remote operation (insert or delete) into our local state.
        This is the magic: it's commutative, associative, idempotent.
        """
        if op.deleted:
            # Remote delete: find and tombstone our local copy
            for c in self._chars:
                if c.id == op.id:
                    c.deleted = True
                    return
        else:
            # Remote insert: find the right sorted position by ID
            for i, c in enumerate(self._chars):
                if c.id > op.id:
                    self._chars.insert(i, op)
                    return
            self._chars.append(op)

    @property
    def text(self) -> str:
        """Return the visible (non-tombstoned) text."""
        return "".join(c.char for c in self._chars if not c.deleted)


# ─── Demo: Same conflict, CRDT way ─────────────────────────────────────────────
doc_a = RGADocument(site_id="A")
doc_b = RGADocument(site_id="B")

# Both start with "abc" — in a real system, initial state is synced
# (simplified: skip initial state sync for clarity)

# The point: concurrent operations just get merged, no transform needed.
# doc_a.local_insert("X", 0) → broadcasts CRDTChar with ID pos~0.5
# doc_b.local_delete(2)       → broadcasts tombstone for 'c'
# Both sides call apply_remote() with the other's op
# Result is always identical regardless of order ✓
```

**架构请求流 / Request Trace:**

```
User A types "X" at position 0
    │
    ▼ Editor sends WebSocket frame
    │  { op: "insert", char: "X", pos: 0, version: 42 }
    │
    ▼ Operation Handler receives
    │  concurrent_ops = history[42:]   ← ops A hasn't seen
    │  transformed = transform(op, concurrent_ops)
    │  apply(transformed) to server doc
    │  append to Op Log
    │
    ▼ Broadcast to all other clients in document room
       { op: "insert", char: "X", pos: 1, version: 43 }  ← transformed!
       (User B's client applies this on top of its local state)
```

This matches the architecture diagram: Editor → WebSocket Gateway → Operation Handler → Op Log → broadcast back.

## Part 3: Edge Cases & Gotchas / 边界情况 (2 min)

### 1. Tombstone 积累 / Tombstone Accumulation (CRDT)

```python
# 问题：大量删除后，_chars 越来越大
# "Hello World" typed then deleted → 11 tombstones remain in memory
# 
# 解法：定期 Compaction（需要全局协调）
# 只有当所有客户端都 >= 某个版本时，才能安全清除 tombstone
# Google Docs 通过定期 snapshot + log replay 解决这个问题
```

### 2. OT 的 TP2 问题 / OT's TP2 Property

Jupiter protocol (Google Docs) uses a simpler "server as single source of truth" model that only requires TP1 (inclusion transformation). TP2 (handling three concurrent ops) is notoriously hard to implement correctly — that's why peer-to-peer OT was abandoned.

### 3. 网络分区 / Network Partition

```
CRDT wins here: offline edits accumulate as local ops.
On reconnect, just apply_remote() all the remote ops.
No conflict — the math guarantees convergence.

OT requires the server version number, so offline OT is tricky.
Google Docs handles this by queuing ops locally and replaying on reconnect.
```

### 4. 意图保留 / Intention Preservation

```python
# 用户意图："删除第二个词"
# 并发操作可能在删除之前插入了一堆内容
# OT 变换后删除了"正确位置"的字符，但可能不是用户想删的那个词
#
# 这是 OT 最深的哲学问题，没有完美解法
# 实践中：用光标 heuristics + 用户 undo 来缓解
```

## Part 5: Interview Simulation / 面试模拟 (3 min)

**Q1: 如果两个用户同时在同一位置插入字符，谁的字符应该排在前面？**

**A1:** This is the "tie-breaking" problem. In OT, server assigns a timestamp or priority based on connection order — whichever op the server receives first wins. In CRDT, each site has a unique ID used for deterministic tiebreaking (e.g., site_id lexicographic order). Neither is "correct" UX-wise; it's a deliberate consistency choice. Some systems let the cursor position communicate intent.

---

**Q2: 为什么 Google Docs 不用 CRDT？**

**A2:** Google Docs predates modern CRDT research (Jupiter Protocol is from 1995/2006). Also, for a centralized product, OT's server-centric model is simpler to reason about for correctness. CRDTs have their own complexity (tombstone management, fractional indexing precision). Google has no strong reason to migrate a system that works at massive scale.

---

**Q3: 如何处理用户离线编辑后重新上线？**

**A3:** 
- **OT approach:** Client stores ops with the last-known server version. On reconnect, sends all queued ops with their original version. Server replays the transform chain. Risky if offline too long (version gap too large) — some systems cap offline time.
- **CRDT approach:** Client accumulates CRDTChar objects locally. On reconnect, exchange ops with server (gossip or vector clock-based sync). apply_remote() handles everything — guaranteed convergence regardless of offline duration.

---

**Q4: 协同编辑系统如何做 Undo/Redo？**

**A4:** This is where things get tricky. Local undo in a collaborative context can "undo" someone else's concurrent work accidentally. Modern systems implement **selective undo**: undo only your own operations, using Exclusion Transformation (ET) to "remove" your past op from the history without affecting others'. Some systems (Figma) implement per-user undo stacks tracked on the server.

---

**Q5: 系统设计面试中，如何在 OT 和 CRDT 之间选择？**

**A5:** Ask these questions:
1. **Need offline-first / P2P?** → CRDT
2. **Central server anyway, proven ops needed?** → OT  
3. **Rich text with complex formatting?** → Yjs (CRDT library) handles this well
4. **Simple shared state (not text)?** → CRDT variants like G-Counter, LWW-Register
5. **Scale?** → Both scale; OT's server bottleneck is the bigger concern at extreme scale

In an interview, showing you know both and can articulate the tradeoffs is more impressive than picking one confidently.
