## Part 1: Theory / 理论基础 (5 min)

### 三种核心推荐算法 / The Three Core Approaches

**1. 协同过滤 (Collaborative Filtering)**

核心思想：用户 A 和用户 B 的历史行为相似，则 A 喜欢的东西 B 可能也喜欢。

- **User-Based CF**：找到与你相似的用户群体，推荐他们喜欢但你还没看过的内容。
- **Item-Based CF**：找到与你互动过的内容相似的其他内容。Netflix 早期用的就是这个。
- **Matrix Factorization（矩阵分解）**：将用户-物品交互矩阵分解为两个低维矩阵（用户嵌入 + 物品嵌入）。这是 Netflix Prize 的获奖方案，现代推荐的基础。

Core idea: If User A and User B have similar historical behavior, what A likes, B will probably also like.

**2. 基于内容的过滤 (Content-Based Filtering)**

根据物品本身的特征（类型、演员、导演、标签）来推荐相似内容。解决冷启动问题（新物品没有交互数据）的关键手段。

Recommends items with similar intrinsic features. Key for solving the **cold start** problem (new items have no interaction data).

**3. 混合方法 (Hybrid)**

生产系统几乎都是混合的。YouTube 的 DNN-based 推荐、TikTok 的双塔模型，本质上都是将多个信号融合成一个统一的排序模型。

Production systems are almost always hybrid. The trick is knowing *when* to apply each.

### 关键心智模型：候选生成 → 粗排 → 精排 / The Funnel Mental Model

```
全量物品池 (数十亿)
    ↓  候选生成 (Candidate Generation)
候选集合 (~1000 items)
    ↓  粗排 (Pre-ranking)
粗排结果 (~100 items)
    ↓  精排 (Ranking)
精排结果 (~20 items)
    ↓  重排 / 业务逻辑 (Re-ranking)
最终展示 (~10 items)
```

Every major recommendation system uses this funnel. The key insight: **each stage trades recall for precision**. At the top, you want to cast a wide net; at the bottom, you apply your most expensive, most accurate model.

### 架构关键路径验证 / Architecture Cross-Check

Let's trace a real request through the system for user `u123` visiting YouTube homepage:

1. **Request arrives** → API Layer receives `GET /feed?userId=u123`
2. **Feature hydration** → Redis lookup: user's watch history embeddings, session context (time of day, device)
3. **Candidate Generation (parallel)**:
   - FAISS ANN search: find top-500 videos whose embeddings are closest to u123's user embedding
   - Item-item CF: pull precomputed "similar to recently watched" list from Redis cache (~300 items)
   - Trending pool: top 200 globally trending (pre-computed, refreshed every 5 min)
   - Dedupe → ~1,000 candidates
4. **Pre-Ranking**: LightGBM model scores all 1,000 with cheap features (category match, recency) → prune to top 100
5. **Ranking**: Deep NN model (DLRM or two-tower) scores 100 candidates with full features → returns P(click), P(watch_30s)
6. **Re-Ranking**: diversity injection (no 3 consecutive videos from same channel), filter watched videos, A/B experiment slot assignment
7. **Response**: Return top 20 video IDs with predicted scores → client renders

**Code path verification against diagram:** Steps 3-4-5-6 map exactly to the four pipeline boxes. ✅

### 核心代码：双塔模型服务端推理 / Two-Tower Model: Serving Architecture

# two_tower_retrieval.py
# The Two-Tower (Dual Encoder) model architecture used by YouTube DNN, TikTok, etc.
# User tower and item tower are trained jointly but served independently.

import numpy as np
from dataclasses import dataclass
from typing import List
import faiss  # pip install faiss-cpu

@dataclass
class UserEmbedding:
    user_id: str
    vector: np.ndarray  # shape: (128,)
    updated_at: float   # unix timestamp

@dataclass 
class ItemEmbedding:
    item_id: str
    vector: np.ndarray  # shape: (128,)

class TwoTowerRetriever:
    """
    Manages ANN index for fast approximate nearest neighbor retrieval.
    
    In production: user embeddings updated every 5 min (stream processing),
    item embeddings updated every 6 hours (batch job).
    """
    
    def __init__(self, embedding_dim: int = 128):
        self.embedding_dim = embedding_dim
        
        # FAISS IVF (Inverted File) index — production choice for >10M items
        # IVFFlat: split vectors into n_clusters, only search relevant clusters
        # Tradeoff: ~10% accuracy loss vs exhaustive search, 100x faster
        n_clusters = 1000  # rule of thumb: sqrt(n_items) for 10M items
        quantizer = faiss.IndexFlatIP(embedding_dim)  # Inner product = cosine similarity (on normalized vectors)
        self.index = faiss.IndexIVFFlat(quantizer, embedding_dim, n_clusters, faiss.METRIC_INNER_PRODUCT)
        
        self.item_ids: List[str] = []  # parallel array: index position → item_id
        self.is_trained = False
        
    def build_index(self, item_embeddings: List[ItemEmbedding]):
        """
        Offline batch job: (re)build the ANN index.
        Called every 6 hours, swapped atomically (blue-green pattern).
        """
        vectors = np.array([e.vector for e in item_embeddings], dtype='float32')
        
        # Normalize to unit vectors — converts cosine similarity to inner product
        faiss.normalize_L2(vectors)
        
        # Train the IVF quantizer (learns cluster centroids via k-means)
        # Requires at least 30 * n_clusters training samples
        self.index.train(vectors)
        self.index.add(vectors)
        
        self.item_ids = [e.item_id for e in item_embeddings]
        self.is_trained = True
        
        # Production note: after building, serialize index to S3
        # faiss.write_index(self.index, '/tmp/item_index.faiss')
        
    def retrieve(self, user_embedding: UserEmbedding, top_k: int = 500) -> List[str]:
        """
        Online serving: retrieve top_k candidates for a given user.
        Target latency: <5ms for 10M items.
        """
        if not self.is_trained:
            raise RuntimeError("Index not built. Run build_index() first.")
        
        query = user_embedding.vector.reshape(1, -1).astype('float32')
        faiss.normalize_L2(query)  # same normalization as at index time
        
        # nprobe: how many clusters to search. Higher = more accurate, slower.
        # Production: nprobe=50 gives ~95% recall@500 with <5ms latency
        self.index.nprobe = 50
        
        distances, indices = self.index.search(query, top_k)
        
        # Convert flat indices back to item IDs; filter -1 (empty slots)
        return [
            self.item_ids[idx] 
            for idx in indices[0] 
            if idx != -1
        ]

class RecommendationPipeline:
    """
    Orchestrates the full retrieval + ranking funnel.
    """
    
    def __init__(self, retriever: TwoTowerRetriever, ranker: RankingModel):
        self.retriever = retriever
        self.ranker = ranker
        
    def get_recommendations(
        self, 
        user_embedding: UserEmbedding,
        user_features: dict,
        item_features_store: dict,  # item_id → features
        n_final: int = 20
    ) -> List[str]:
        
        # Stage 1: Candidate Generation (~1000 items)
        candidates = self.retriever.retrieve(user_embedding, top_k=500)
        # (In practice, merge with CF-based and trending pools here)
        
        # Stage 2: Ranking (score all candidates)
        scored = []
        for item_id in candidates:
            if item_id not in item_features_store:
                continue  # item not in catalog (e.g., deleted)
            score = self.ranker.score(user_features, item_features_store[item_id])
            scored.append((item_id, score))
        
        # Sort by score descending
        scored.sort(key=lambda x: x[1], reverse=True)
        
        # Stage 3: Re-ranking (diversity injection)
        final = self._inject_diversity(scored, n_final)
        return final

### 特征工程：实时 vs 离线 / Feature Engineering: Real-Time vs Offline

```python
# feature_store_client.py
# Production systems use a feature store (Feast, Tecton, or custom) 
# to serve features with consistent definitions between training and serving.

import redis
import json
from typing import Dict, Any, Optional

class FeatureStoreClient:
    """
    Unified interface for online (Redis) and offline (S3/Hive) features.
    
    Key insight: Training/serving skew is the #1 cause of recommendation 
    quality degradation. A feature store ensures the same feature computation 
    logic is used at both training time and serving time.
    """
    
    def __init__(self, redis_client: redis.Redis):
        self.redis = redis_client
        
    def get_user_features(self, user_id: str) -> Optional[Dict[str, Any]]:
        """
        Fetch real-time user features from Redis.
        
        What's stored:
        - user_embedding: 128-dim float vector (updated every 5 min by Flink)
        - recent_categories: top-3 categories clicked in last hour (stream)
        - session_count_today: integer counter (atomic increment)
        - historical_ctr: click-through rate across all sessions (batch, updated hourly)
        """
        raw = self.redis.get(f"user_features:{user_id}")
        if raw is None:
            # Cold start: new user, return default features
            return self._default_user_features()
        return json.loads(raw)
    
    def get_item_features(self, item_id: str) -> Optional[Dict[str, Any]]:
        """
        Fetch item features.
        
        What's stored:
        - item_embedding: 128-dim float vector (updated every 6h by batch job)
        - global_ctr_7d: click-through rate over last 7 days (batch)
        - freshness_score: decay function of item age (recomputed every 15 min)
        - creator_id: string (static)
        - category: enum (static)
        """
        raw = self.redis.get(f"item_features:{item_id}")
        if raw is None:
            return None  # item not in catalog
        return json.loads(raw)
    
    def _default_user_features(self) -> Dict[str, Any]:
        """
        For new users: use global popular items (popularity-based fallback).
        This is the standard cold-start solution.
        """
        return {
            "user_embedding": [0.0] * 128,  # zero vector → will match popular items
            "recent_categories": [],
            "session_count_today": 0,
            "historical_ctr": 0.05  # global average CTR
        }
    
    def update_user_embedding(self, user_id: str, new_embedding: list, ttl_seconds: int = 86400):
        """
        Called by Flink stream job after processing user events.
        TTL ensures stale embeddings don't persist indefinitely.
        """
        current = self.get_user_features(user_id) or {}
        current["user_embedding"] = new_embedding
        self.redis.setex(
            f"user_features:{user_id}",
            ttl_seconds,
            json.dumps(current)
        )
```

## Part 3: Edge Cases & Gotchas / 边界情况 (2 min)

**1. 冷启动问题 (Cold Start Problem)**
- **新用户**：没有历史数据。解法：展示全局热门内容 + 引导用户声明偏好（onboarding）+ 利用 demographic 特征。
- **新物品**：没有交互数据。解法：基于内容特征（标签、分类、文本嵌入）建立 item embedding；初始时给予曝光保障（exploration）。

**2. 过滤气泡 (Filter Bubble)**
如果只推荐用户已经喜欢的，会越来越窄。解法：在 re-ranking 阶段主动注入多样性（MMR、随机探索比例）。

**3. 位置偏差 (Position Bias)**
用户更可能点击排名靠前的内容，不代表它真的更好。在训练时需要对 position 做去偏处理（position debiasing）。

**4. 时效性 vs 相关性 (Freshness vs Relevance)**
老内容的 CTR 数据更丰富但可能过时；新内容没有 CTR 但可能更及时。解法：freshness score（时间衰减函数）+ 新内容曝光保障。

**5. 训练-服务偏差 (Training/Serving Skew)**
训练用历史 batch 数据，服务时用实时数据——如果特征计算逻辑不一致，模型会降级。Feature Store 是标准解法。

**6. 数据飞轮 (Data Flywheel)**
更好的推荐 → 更多用户 → 更多数据 → 更好的模型。但也意味着马太效应：头部内容被推荐越多，尾部内容越来越难被发现。

## Part 4: Real-World Application / 实际应用 (2 min)

### YouTube: Deep Neural Network for Recommendations (2016)
Google 在 2016 年发表的论文描述了两阶段架构：候选生成网络（softmax over item embedding space）+ 排序网络（DNN predicting watch time）。这是业界第一个将深度学习规模化应用于推荐的里程碑。
> Paper: https://research.google.com/pubs/pub45530.html

### TikTok: Dual Encoder + Realtime Feedback Loop
TikTok 的核心竞争力在于**超快的反馈循环**：用户每完成一个视频，信号（watch time, replay, share）在秒级内更新用户 embedding，下一条推荐立即反映。这就是"越刷越准"的工程本质。

### Netflix: Offline Evaluation with A/B Testing
Netflix 的工程博客详细描述了如何用离线指标（nDCG, recall@k）做快速实验筛选，再用在线 A/B test 验证真实业务指标（retention, watch time）。绝大多数离线表现好的模型上线后效果一般——这提醒我们 **offline metrics ≠ online metrics**。

### Feature Engineering at Scale: Uber Michelangelo
Uber 的 Michelangelo 平台是业界公开的最完整的 ML 平台案例，其 Feature Store 解决了"同一特征在训练和推理时要保持完全一致"的工程难题。值得深读。
> Blog: https://www.uber.com/blog/michelangelo-machine-learning-platform/

## Part 5: Interview Simulation / 面试模拟 (3 min)

**Q1: How would you handle the cold start problem for new users?**

A: Two-pronged approach. Short-term: show globally popular items, use any available signals (device type, geo, time of day). Long-term: onboarding flow where user explicitly declares interests; these explicit signals are extremely high-value. Once the user has 5-10 interactions, switch to personalized recommendations.

**Q2: How do you ensure the recommendation system doesn't create a filter bubble?**

A: Enforce diversity constraints at the re-ranking stage. Two techniques: (1) **Determinantal Point Process (DPP)** — mathematically maximizes diversity while preserving relevance; (2) **ε-greedy exploration** — dedicate 10-15% of recommendation slots to "exploration" (novel categories, emerging creators). Also track diversity metrics (intra-list diversity, catalog coverage) in your A/B test dashboards.

**Q3: The ranking model starts degrading after a few months. What do you do?**

A: Likely causes: (1) **distribution shift** — user behavior changed, model trained on stale data; (2) **feature drift** — upstream feature pipeline changed but model wasn't retrained. Solution: implement **continuous training** (retrain model weekly/daily on fresh data). Monitor feature distributions with alerts on statistical drift (KL divergence). Use a Champion/Challenger framework to always have a fresh challenger model ready.

**Q4: How would you design the system to handle 10M concurrent users at peak?**

A: The key is pre-computation. You can't run full retrieval + ranking in real-time for everyone. Strategies: (1) **Pre-compute recommendations** for your top 5% most active users every 5 minutes (they drive 80% of traffic); (2) **Cache retrieval candidates** — user embeddings change slowly, so cache the ANN search results for 5-10 minutes; (3) **Stateless ranking servers** behind a load balancer — ranking is CPU/GPU bound and scales horizontally; (4) Feature hydration via Redis with local read replicas near each ranking server.

**Q5: How do you measure if your recommendation system is actually good?**

A: Never rely on a single metric. Offline: precision@k, recall@k, nDCG (normalized discounted cumulative gain), AUC on held-out test set. Online: CTR, watch time per session, D7/D30 retention. Business: revenue per user, subscriber growth. Crucially, watch for **Goodhart's Law** — optimizing CTR alone leads to clickbait. Use a balanced scorecard. Also track long-term metrics like catalog coverage and diversity to avoid the filter bubble trap.
