🏗️ 系统设计 / System Design — Day 147

架构选型决策树：从单体到微服务的演进路径

Architecture Decision Tree: The Evolution from Monolith to Microservices

📊 Synthesis Day — Expert Level | 综合之前覆盖的所有架构主题

想象你在设计... / The Scenario

你是某 500 人公司的 Staff Engineer。CEO 问你："我们该不该把单体拆成微服务？"

这不是一个技术问题——这是一个商业决策。正确答案取决于你所处的阶段。

架构演进的四个阶段 / Four Stages of Architecture Evolution

Stage 1: 单体起步 Stage 2: 数据库成为瓶颈 ┌─────────────────────┐ ┌───────┐ ┌────────┐ │ Monolith │ │ App │ │ App │ │ [All-in-one] │ → └───┬───┘ └───┬────┘ │ Single DB │ └──────┬──────┘ └─────────────────────┘ ┌───────▼──────┐ │ DB Primary │ │ + Replica(s)│ └──────────────┘ Stage 3: 读写分离 + 缓存 Stage 4: 服务按业务边界拆分 ┌──────────────────────┐ ┌──────────┐ ┌──────────┐ │ App │ │ Service A│ │ Service B│ │ ↕ Redis Cache │ → └────┬─────┘ └────┬─────┘ │ DB Primary (writes) │ │ Message │ │ DB Replica (reads) │ └───► Queue ◄──┘ └──────────────────────┘ ┌──────────────────┐ (Day 6: Caching) │ DB per service │ (Day 7-8: Indexing/Replication) │ (or shared+split)│ └──────────────────┘ (Day 11: Consistent Hashing) (Day 12: CAP Theorem)

关键决策节点 / Key Decision Points

🟢 何时保持单体 (Stay Monolith)

  • 团队 < 50 人，代码库可以在一个 IDE 里全部理解
  • 每个模块的负载相似，没有明显的性能热点
  • 真实案例：Shopify、Stack Overflow 长期跑单体，业务仍然健康

🟡 何时优先扩展数据库（不拆服务）

  • 触发点：DB 成为瓶颈（监控 slow_query_log，p99 延迟上升）
  • 动作顺序：加索引 → 读写分离 → 引入缓存层 (Day 6, 7, 8)
  • 这一步收益最大，架构代价最小，优先于微服务拆分

🔴 何时真正需要微服务

  • 不同模块有截然不同的扩展需求（搜索 vs 支付 vs 通知）
  • 不同团队需要独立部署节奏，部署耦合成为业务瓶颈
  • 触发点：不是"感觉需要"，是 oncall 告诉你哪个服务在拖累全局

为什么这样设计？/ Key Insight

核心原则：架构决策应该跟随组织规模，而不是超前于它。

Conway's Law 说：系统的架构会镜像产生它的组织通信结构。

  • 团队还没分组？单体自然。
  • 团队按业务线分组？微服务自然。
  • 强行逆势而为 → 要么无人维护的服务，要么紧耦合的"分布式单体"。

常见错误 / Common Mistakes

❌ "Microservices-first" — 未验证产品需求就开始拆分。Netflix 也是先跑了多年单体才拆的。

❌ 拆了服务没拆数据 — 多个服务共享同一个 DB schema。这不是微服务，这是分布式单体，两套代价、一套收益。

❌ 跳过 Stage 2/3 — 直接从单体跳到微服务，忽略了成本更低的数据库优化阶段。

❌ 忽略 Consistent Hashing (Day 11) — 水平扩展时缓存失效，命中率崩溃，流量全压到 DB。

✅ **正确姿势**：Profile 真实瓶颈 → 最小化改动解决 → 验证效果 → 再下一步。

#518 Coin Change II 🟡 Medium

  • 🔗 https://leetcode.com/problems/coin-change-ii/
  • 📹 https://neetcode.io/problems/coin-change-ii

模式回顾 / Pattern Recap (4th problem in block)

之前的题：

  • #62 Unique Paths → dp[i][j] = dp[i-1][j] + dp[i][j-1] （计数路径）
  • #1143 LCS → dp[i][j] = match ? dp[i-1][j-1]+1 : max(dp[i-1][j], dp[i][j-1])
  • #309 Stock Cooldown → 状态机 DP，hold/sold/cooldown

今天的变化 / What's different today:

Coin Change II 是无界背包（Unbounded Knapsack）——每枚硬币可以无限次使用。这不同于 LCS 的"用完就没"，也不同于 Unique Paths 的纯方向移动。关键区别：dp[i][j-coins[i-1]] 而非 dp[i-1][j-coins[i-1]]（允许重复用同一个物品）。

现实类比 / Real-World Analogy

想象你去超市，只有 1 元、5 元、10 元的硬币，想凑出刚好 15 元。有多少种凑法？

  • [10, 5], [10, 1, 1, 1, 1, 1], [5, 5, 5], [5, 5, 1×5], ...

Coin Change II 就是枚举所有这些组合数。

问题 / Problem

给定硬币面额数组 coins 和目标金额 amount，返回凑出该金额的组合数（不计顺序）。

# Example
coins = [1, 2, 5], amount = 5
# Output: 4
# [1,1,1,1,1], [1,1,1,2], [1,2,2], [5]

如何映射到模板 / Mapping to 2-D DP Template

dp[i][j] = 用前 i 种硬币凑出金额 j 的组合数 i → coins (行) j → amount 0..amount (列) 状态转移： 不用 coin[i]: dp[i][j] = dp[i-1][j] 用 coin[i]: dp[i][j] += dp[i][j - coin[i]] ← 注意是 dp[i], 不是 dp[i-1]！ ← 因为硬币可重复使用 Base case: dp[i][0] = 1 (凑出 0 元只有一种方法：什么都不选)

Python 解法 + 追踪 / Solution with Trace

def change(amount: int, coins: list[int]) -> int:
    # 2-D DP: dp[i][j] = ways using first i coins to make amount j
    n = len(coins)
    dp = [[0] * (amount + 1) for _ in range(n + 1)]
    
    # Base case: 0 ways using 0 coins, except amount=0
    for i in range(n + 1):
        dp[i][0] = 1  # 1 way to make 0: choose nothing
    
    for i in range(1, n + 1):
        for j in range(1, amount + 1):
            dp[i][j] = dp[i-1][j]  # don't use coin[i-1]
            if j >= coins[i-1]:
                dp[i][j] += dp[i][j - coins[i-1]]  # use coin[i-1] (reusable!)
    
    return dp[n][amount]

# Trace: coins=[1,2,5], amount=5
# dp[0]: [1, 0, 0, 0, 0, 0]   (0 coins, only j=0 is valid)
# dp[1] (coin=1): [1, 1, 1, 1, 1, 1]  (all amounts via 1s)
# dp[2] (coin=2): [1, 1, 2, 2, 3, 3]
# dp[3] (coin=5): [1, 1, 2, 2, 3, 4]  ← dp[3][5] = dp[2][5] + dp[3][0] = 3+1 = 4 ✓

空间优化（重要！）/ Space Optimization:

def change(amount: int, coins: list[int]) -> int:
    # Optimize to O(amount) space
    # Key: iterate coins outer, amount inner (ensures unbounded use)
    dp = [0] * (amount + 1)
    dp[0] = 1
    
    for coin in coins:
        for j in range(coin, amount + 1):
            dp[j] += dp[j - coin]
    
    return dp[amount]

# Time: O(n * amount), Space: O(amount)
# IMPORTANT: outer=coins, inner=amount → each coin counted unlimited times
# If reversed: outer=amount, inner=coins → 0/1 knapsack (each coin once)

  • 时间: O(n × amount) — 填满二维表
  • 空间: O(amount) — 压缩为一维后

STAR 框架拆解 / STAR Breakdown

🌟 情境 / Situation

新来的 Staff，没有直接汇报关系，800ms p99 已影响转化率，但每个工程师对根因判断不同——有人说是 DB 慢查询，有人说是第三方 API，有人说是 N+1 请求。

📋 任务 / Task

在 6 个月内 将 p99 从 800ms → 200ms，同时：

  1. 不停服
  2. 不影响产品新功能交付

⚡ 行动 / Action

Phase 1：用数据结束争论（第 1-2 周）

  • 部署分布式追踪（Jaeger/Datadog APM），生成 flame graph
  • 画出 p95/p99/p999 分布曲线，找出是高频慢还是偶发极慢
  • 以事实说话，终止"感觉是 DB"之类的争论

Phase 2：找最大杠杆点（第 3-4 周）

  • 发现 60% 延迟来自同一批 3 个端点，且都触发了 N+1 查询
  • 优先解决：不需要重架构，风险低，预估可改善 300-400ms

Phase 3：并行推进，不 block 产品（第 5-16 周）

  • 把优化工作切成 2 周 sprint，每 sprint 一个可测量目标
  • 给产品团队每周一更新："本周 p99 降了 X ms，你们的功能 Y 我们协调好时间窗"
  • 建立 feature flag — 优化版上线先灰度 5%，有问题立即回退

Phase 4：巩固与防退化（第 4-6 月）

  • 在 CI 中加 performance regression test，新 PR 不能让 p99 回升
  • 写内部 RFC 记录决策，避免新人重踩同一个坑

📊 结果 / Result

5 个月时达标（p99: 190ms），产品零功能延期，团队形成了"先量化再动手"的文化共识。

  4. 影响圈 vs 关注圈：产品要求不 block 功能是你的关注圈，怎么优化是你的影响圈，聚焦影响圈

React 性能综合：你真的需要 memo 吗？

React Performance Synthesis: Do You Actually Need memo?

综合日 — Expert Level | 整合 Day 34/36 的 memoization 主题 + 实战决策框架

场景 / Scenario

你在做一个实时 dashboard，有 50 个 widget，每秒刷新数据。产品说"感觉有点卡"。你的第一反应是什么？

错误答案：立刻给所有组件加 React.memo。

正确答案：先量化，再精准优化。

实战代码 / Code Snippet

// ❌ 常见错误：memo 到处加，实际没有帮助
const Widget = React.memo(({ data, onUpdate }) => {
  return <div onClick={() => onUpdate(data.id)}>{data.value}</div>;
});

// 问题：onUpdate 每次渲染都是新函数引用
// React.memo 做的是浅比较，onUpdate 永远不等于上次的 onUpdate
// 结果：memo 完全没用，还多了一层比较开销

// ✅ 正确做法：memo + useCallback 配合
const Dashboard = () => {
  const [widgets, setWidgets] = useState(initialWidgets);
  
  // useCallback 稳定 onUpdate 的引用
  const handleUpdate = useCallback((id: string) => {
    setWidgets(prev => prev.map(w => w.id === id ? refresh(w) : w));
  }, []); // deps: empty → stable reference

  return (
    <>
      {widgets.map(w => (
        <Widget key={w.id} data={w} onUpdate={handleUpdate} />
      ))}
    </>
  );
};

const Widget = React.memo(({ data, onUpdate }: WidgetProps) => {
  // Now memo works: data ref changes only when that widget's data changes
  // onUpdate ref is stable (from useCallback)
  return <div onClick={() => onUpdate(data.id)}>{data.value}</div>;
});

猜猜输出 / Quiz

const Parent = () => {
  const [count, setCount] = useState(0);
  const handler = () => console.log('clicked');
  
  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>+</button>
      <MemoChild onClick={handler} label="static" />
    </>
  );
};

const MemoChild = React.memo(({ onClick, label }) => {
  console.log('MemoChild rendered');
  return <button onClick={onClick}>{label}</button>;
});

点击 + 按钮后，MemoChild rendered 会打印吗？

A. 不会，因为用了 React.memo

B. 会，因为 handler 每次是新函数引用

C. 不会，因为 label 没变

D. 会，因为父组件状态改变了

<details><summary>显示答案 / Show Answer</summary>

答案：B — 会打印。

handler 在每次 Parent 渲染时都是全新的函数对象（引用不同）。React.memo 做浅比较，发现 onClick prop 变了，就会重新渲染 MemoChild。

修复：const handler = useCallback(() => console.log('clicked'), []);

</details>

❌ vs ✅ 对照 / Common Mistakes

❌ 误区✅ 正确
memo 随手加先 Profile（React DevTools Profiler）再加
memo 不配 useCallback两者配合才有效果
useMemo 缓存简单计算useMemo 适合 >1ms 的计算，简单值不值得
以为 memo 能解决所有卡顿Context value 变化会绕过 memo！

何时用 / 何时不用 / Decision Framework

应该用 memo 的场景:
✅ 组件渲染耗时 >1ms（Profile 确认）
✅ 父组件高频更新但子组件 props 很少变化
✅ 子组件有复杂子树（列表中的列表）

不需要 memo 的场景:
❌ 组件本身渲染很快（<0.1ms）
❌ Props 每次都会变（如 new Date()、inline object）
❌ 只是感觉应该加（要有数据支撑！）

Context 的特殊问题:
⚠️ 任何消费了 Context 的组件，当 Context value 变化时
   会重新渲染，即使有 memo
解决：拆分 Context / 用 useMemo 稳定 value

🧒 ELI5

React.memo 就像收快递时签收记录——"如果包裹内容没变，我就不拆开"。但如果快递员每次都换一个新袋子装同样的东西，签收系统就以为每次都是新包裹。useCallback 的作用就是保证每次递送用同一个袋子，这样 memo 才真正有效。

  • Windows: 据报道约 65 tokens/sec（GPT-OSS-120B）
  • Linux native: 据报道约 14 tokens/sec

根因：固件的 GPU 功耗表被加密，只有 Windows 驱动能解密。Linux 内核无法读取，GPU 被锁在低频模式。WSL（Linux on Windows）是目前性能最接近 Windows 的妥协方案。

对你的意义 / Takeaway:

  • 选 AI 开发硬件时，Linux 兼容性不是理所当然
  • "Open Ecosystem" 与 "Proprietary Firmware" 的矛盾在 AI 加速硬件领域仍然尖锐
