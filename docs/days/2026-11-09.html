分布式系统一致性模型深度对比 — From Redis to Spanner

想象你在设计...

你是技术负责人，面对三个不同的存储选型问题：

  1. 用户 session — 丢数据无所谓，速度第一
  2. 库存扣减 — 超卖一次损失巨大
  3. 全球用户档案 — 需要跨区域读写、强一致

这三个场景需要完全不同的一致性模型。

一致性模型谱系 (Consistency Spectrum)

Weak Eventual Strong Linearizable | | | | Redis Cache Cassandra DynamoDB Spanner (no sync) (tunable) (single-key) (global txn) ← 延迟低、可用高 延迟高、可用受限 →

四种核心模型:

1. Weak Consistency (弱一致)

  • 写完不保证立刻可读
  • 典型: CPU Cache, Redis (默认)
  • 场景: 限流计数器、view count，错一点无所谓

2. Eventual Consistency (最终一致)

  • 最终收敛，不保证何时
  • 典型: Cassandra, DynamoDB (eventually consistent reads), DNS
  • 场景: 社交 feed、用户 profile、购物车

3. Strong Consistency (强一致)

  • 读到最新写入
  • 典型: DynamoDB (strongly consistent reads), RDBMS (single node)
  • 场景: 账户余额、读-改-写需要串行化

4. Linearizability / External Consistency

  • 所有操作有全局时间顺序，像单机一样
  • 典型: Google Spanner (TrueTime API), etcd, ZooKeeper
  • 场景: 分布式锁、金融转账跨行、分布式 CAS

为什么这样设计？关键权衡

CAP vs PACELC:

  • CAP 只描述分区时的选择 (CP or AP)
  • PACELC 补充了正常运行时的选择: 延迟 vs 一致性
  • 真实系统更多是 PACELC 问题，网络分区是小概率事件

Cassandra 的 Quorum 魔法:

W + R > N → 保证至少一个节点重叠 → 读到最新写 N=3, W=2, R=2 → 强一致 (but slower) N=3, W=1, R=1 → 弱一致 (but fast) N=3, W=1, R=3 → read-heavy strong (rarely used)

Spanner 的 TrueTime:

Google 用 GPS + 原子钟，把时间不确定性压到 <7ms，然后等待这个窗口再提交事务 → 全球 linearizable 但有延迟代价。

别踩这个坑 (Common Mistakes)

❌ 误区1: "我们用 Cassandra，所以要强一致就全设 W=N, R=N"

→ 性能断崖。真正需要强一致的数据应该换 DB，不要强拧 Cassandra。

❌ 误区2: "微服务间用最终一致性，加个重试就好了"

→ 没有幂等性设计的重试 = 数据翻倍。Outbox Pattern + idempotency key 是标配。

❌ 误区3: 分布式锁用 Redis SETNX 就够了

→ Redis 故障转移窗口内锁会失效。高风险场景用 Redlock 或直接 etcd。

🧒 ELI5

想象你家有三个人共用同一个银行账户：妈妈、爸爸、你。

  • 弱一致 = 各自记小本子，偶尔对一下，可能有人多花了钱
  • 最终一致 = 每晚同步一次，白天可能有出入，但第二天一定对齐
  • 强一致 = 每次花钱都要打电话给全家人确认，慢但不会超支
  • Linearizable = 全家人都在同一个房间，一个人买东西所有人立刻知道

#72 Edit Distance — 编辑距离

🔗 https://leetcode.com/problems/edit-distance/

🟡 Medium

📹 https://www.neetcode.io/problems/edit-distance

现实类比 / Real-World Analogy

想象你在做拼写检查器。用户输入 "horse"，正确词是 "ros"。

你需要计算最少几步操作（插入、删除、替换）把一个词变成另一个词。

这就是编辑距离，Git diff、DNA 序列比对、搜索纠错都用这个。

Imagine building a spell checker: user typed "horse", correct is "ros". How many insert/delete/replace operations to transform one to the other? That's edit distance — used in Git diff, DNA alignment, search autocomplete.

问题定义

Input: word1 = "horse", word2 = "ros" Output: 3 Explanation: horse → rorse (replace h→r) rorse → rose (delete r) rose → ros (delete e)

操作代价: insert=1, delete=1, replace=1

映射到2-D DP模板

# Template:
# dp = [[0] * (m+1) for _ in range(n+1)]
# for i in range(1, n+1):
#     for j in range(1, m+1):
#         dp[i][j] = TRANSITION(dp[i-1][j], dp[i][j-1], dp[i-1][j-1])

# For Edit Distance:
# dp[i][j] = min edit distance between word1[:i] and word2[:j]

State: dp[i][j] = minimum operations to convert word1[:i] → word2[:j]

Base cases:

  • dp[0][j] = j (insert j chars from empty string)
  • dp[i][0] = i (delete i chars to reach empty string)

Transition (这就是关键):

if word1[i-1] == word2[j-1]:
    dp[i][j] = dp[i-1][j-1]          # 字符相同，不需要操作
else:
    dp[i][j] = 1 + min(
        dp[i-1][j],    # delete from word1
        dp[i][j-1],    # insert into word1
        dp[i-1][j-1]   # replace
    )

完整解法 + 手动追踪

def minDistance(word1: str, word2: str) -> int:
    n, m = len(word1), len(word2)
    
    # Build dp table with base cases
    dp = [[0] * (m + 1) for _ in range(n + 1)]
    
    # Base cases: empty string transformations
    for i in range(n + 1):
        dp[i][0] = i  # delete all chars from word1
    for j in range(m + 1):
        dp[0][j] = j  # insert all chars from word2
    
    for i in range(1, n + 1):
        for j in range(1, m + 1):
            if word1[i-1] == word2[j-1]:
                dp[i][j] = dp[i-1][j-1]  # free diagonal move
            else:
                dp[i][j] = 1 + min(
                    dp[i-1][j],    # delete
                    dp[i][j-1],    # insert
                    dp[i-1][j-1]   # replace
                )
    
    return dp[n][m]

追踪 "horse" → "ros":

"" r o s "" 0 1 2 3 h 1 1 2 3 o 2 2 1 2 r 3 2 2 2 s 4 3 3 2 e 5 4 4 3 ← answer: 3

画出这个表格，每个格子只看三个方向（上、左、左上），立刻就懂转移规律。

Complexity: Time O(n×m), Space O(n×m) → can optimize to O(m) with rolling array

空间优化 (Space O(m))

def minDistance(word1: str, word2: str) -> int:
    m = len(word2)
    prev = list(range(m + 1))  # prev row
    
    for i, c1 in enumerate(word1, 1):
        curr = [i] + [0] * m
        for j, c2 in enumerate(word2, 1):
            if c1 == c2:
                curr[j] = prev[j-1]
            else:
                curr[j] = 1 + min(prev[j], curr[j-1], prev[j-1])
        prev = curr
    
    return prev[m]

🗣️ 软技能 / Soft Skills — Day 151 (Synthesis)

综合深化 / Expert Synthesis: 60道行为面试题全部完成。今天综合演练——在技术面试中应对多维压力场景。

场景题: 技术领导者的困境 — 当速度、质量、团队情绪三角失衡

Senior/Staff-Level Scenario:

"你接手了一个关键项目：上线日期是六周后，但你发现现有架构设计有严重的技术债，推上线后六个月内必然出现生产故障。团队士气已经很低（之前的 lead 刚离职），产品和高管都在期待按时交付。你怎么做？"

为什么这道题难

这不是一道只有一个答案的题。面试官在考察：

  1. 你是否能识别真正的风险（不只是说"有技术债"）
  2. 你是否懂得如何争取资源/时间（不是直接对抗）
  3. 你如何管理向上和向下的关系

STAR 分解框架

Situation (情境):

描述清楚背景复杂度。不要说"有技术债"，要说具体的：

"架构中有一个单点 DB，在当前设计下，DAU 超过 50k 时会出现锁竞争，而产品上线后第一周预计 DAU 就会达到 80k。"

Task (任务):

明确你的角色和约束：

"我是唯一了解底层架构的 senior engineer，同时还要带两个 junior 成员。"

Action (行动) — 这是核心，展开讲:

  1. 量化风险，不要模糊 — 写一页技术风险文档，包括：触发条件、预期影响（故障率/用户影响）、修复时间。数字比"可能会有问题"有力得多。
  1. 提供选项，不是问题 — 不要只来汇报"我们有麻烦"，要带三个选项：

- Option A: 按期上线（接受技术风险，提供监控+回滚方案）

- Option B: 延期 2 周修复核心风险点（什么要改，什么不动）

- Option C: 全量重构（成本/收益不合算，排除）

  1. 赢得团队信任 — 在团队里坦诚技术债的现状，不要 sugarcoat，但也要给出清晰的计划让大家有方向感。"我们知道哪里有问题，我们有计划"比"别担心"更安心。
  1. 向上对齐 — 和 PM/高管 1:1，用业务语言沟通风险："如果按期上线，我们 70% 的概率在 Q2 会有一次重大故障，影响 X 用户，修复需要 Y 工程师周。延期 2 周能把这个概率降到 15%。你来决定。"

Result (结果):

描述最终结果，以及 你学到了什么：

"最终选择了 Option B，延期 2 周，上线后稳定运行。团队信任度提升——大家知道技术问题会被如实沟通，不被掩盖。"

❌ Bad vs ✅ Good

❌ 踩雷✅ 加分
"我告诉他们有技术债，但他们不听""我量化了风险，给了三个选项让他们选"
"我们团队决定延期""我起草了风险分析文档，推动了对话"
"最终按时上线了""最终选择了延期 2 周，并说清楚了权衡"
"我很担心质量""我建立了监控 + 回滚方案，把上线风险降低到可接受范围"

Senior/Staff Tips

  • Staff level 的核心能力：把技术风险转化为业务语言。"锁竞争"对 PM 没意义，"上线后两个月内 20% 的用户会遇到超时"有意义。
  • 永远带着方案来，不要只来汇报问题。这是区分 IC 和领导力的关键信号。
  • 团队士气管理：透明 > 乐观。Junior 工程师知道有技术债时，真正让他们不安的是"领导知道但不说"。

Key Takeaways

  1. 量化技术风险，用业务语言表达
  2. 给选项，让决策者选，而不是单方面决定
  3. 向下透明，向上提方案
  4. 把困境变成建立信任的机会

🧒 ELI5

想象你发现了学校报告里有个大错误，但报告明天就要交。

聪明的做法不是偷偷改掉，也不是大哭大闹说"全错了"——

而是去找老师说："这里有个问题，我有三个方案，你来选。"

这就是 senior 的处理方式：把问题变成决策，而不是让别人解决你的焦虑。

🔧 1. Google 发布第八代 AI 芯片两款新型号

来源: https://blog.google/innovation-and-ai/infrastructure-and-cloud/global-network/tpu-8i-max-and-8tx/

Google 宣布推出 TPU 8tx 和 8i Max 两款新型 AI 芯片。TPU 8tx 专为政府机构和受监管企业的保密计算（confidential computing）设计，而 8i Max 则面向需要大上下文窗口的 AI 应用。

加上今年 4 月已发布的 TPU 8t 和 8i，Google 在 2026 年内共推出了四款第八代 TPU。

为什么重要 / Why it matters:

  • 保密计算 TPU 是 Google 攻占政务云和金融云市场的关键武器
  • 大上下文窗口需求驱动专用硬件——通用芯片内存带宽不够
  • 芯片迭代速度加快，AI 算力"军备竞赛"在硬件层持续升温

Google announced two new eighth-gen AI chips: TPU 8tx for confidential computing and 8i Max for large context window AI applications, bringing their 2026 TPU lineup to four variants.

🔒 2. OpenAI AI 模型在 Linux 内核中发现据报道 948 个安全漏洞

来源: https://openai.com/index/a-thousand-fewer-paths-to-root/

OpenAI 表示，使用其即将发布的网络安全模型，自主扫描了截至 2026 年 10 月中旬的 Linux 内核代码，据报道发现了 948 个本地权限提升（local privilege escalation）漏洞，并为这些漏洞生成了补丁，经人工研究员审查。

为什么重要 / Why it matters:

  • AI 做安全扫描从"辅助工具"升级为"自主发现"——质变
  • 若属实，这是 AI 对开源基础设施最大规模的安全贡献之一
  • 也引发讨论：同样的模型能不能被攻击者用来"找漏洞不补漏洞"？

OpenAI claims its upcoming cyber model autonomously found reportedly 948 Linux kernel privilege escalation vulnerabilities and generated patches, reviewed by human researchers.

☁️ 3. 微软据报道正在"收缩"与 Oracle 的云 AI 协议

来源: https://www.bloomberg.com/news/articles/2026-11-06/microsoft-is-winding-down-oracle-deal-to-rent-ai-cloud-capacity

Bloomberg 报道，微软正在重新考虑从 Oracle 等"新云"（neocloud）租用服务器容量的协议，据报道已停止使用其 2023 年与 Oracle 签订合同中的部分算力。原因是 Oracle 提供的算力使用的是较旧的 Nvidia 芯片，对微软而言价值下降。

为什么重要 / Why it matters:

  • 新一代 AI 芯片更新速度快，旧芯片的租用价值快速贬值
  • 微软自建算力能力增强，减少对外部云的依赖
  • "AI 算力泡沫"的讨论再起：大量 neocloud 的商业模式面临考验

Bloomberg reports Microsoft is winding down cloud capacity rentals from Oracle, reportedly due to older Nvidia chips becoming less useful as Microsoft builds its own infrastructure.

如果你在做 AI 基础设施相关工作，今年最重要的判断是：买还是租算力，租谁的，租多久。
