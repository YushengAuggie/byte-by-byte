🏗️ 系统设计 / System Design — Day 153 (Synthesis)

分布式事务模式全比较：SAGA vs 2PC vs Outbox Pattern

想象你在设计…

你在构建一个电商平台（像我们 Day 38 设计的 Stripe 支付系统 + Day 36 的 E-Commerce Platform）。用户下单时需要同时：

  1. 扣减库存
  2. 创建订单
  3. 扣款
  4. 发送确认邮件

这四步分布在四个不同的微服务上。任何一步失败都需要回滚。如何保证分布式事务的一致性？

ASCII 架构对比

┌─────────────────────────────────────────────────────┐ │ 分布式事务三大模式 │ └─────────────────────────────────────────────────────┘ 2PC (Two-Phase Commit): Coordinator ──→ Phase 1: "准备好了吗?" ──→ [ServiceA, ServiceB, ServiceC] Coordinator ←── Phase 1 Response: "YES" ←── [all vote] Coordinator ──→ Phase 2: "提交!" ──→ [ServiceA, ServiceB, ServiceC] ⚠️ 协调者宕机 = 所有参与者阻塞 SAGA (Choreography): OrderService ──→ [event: OrderCreated] ↓ InventoryService ──→ [event: InventoryReserved] ↓ PaymentService ──→ [event: PaymentFailed] ↓ InventoryService ←── [compensate: ReleaseInventory] ← 补偿事务 OrderService ←── [compensate: CancelOrder] Transactional Outbox: ┌──────────────┐ ┌────────────────┐ ┌──────────────┐ │ Service DB │ │ Outbox Table │ │ Message Bus │ │ order: saved │ ── │ event: pending │ ──→│ Kafka/SQS │ │ (same TX) │ │ (atomic write) │ │ │ └──────────────┘ └────────────────┘ └──────────────┘ CDC (Debezium) or polling pulls outbox → publishes events

为什么这样设计？关键权衡

模式一致性可用性复杂度适用场景
2PC强一致性❌ 低（协调者是单点）中等金融核心账本、跨库同一数据中心
SAGA最终一致性✅ 高高（需补偿逻辑）微服务、跨服务工作流
Outbox至少一次✅ 高中等保证"事件一定发出去"

核心原则：CAP 定理（Day 12）告诉我们，分布式系统无法同时保证 C + A + P。SAGA 选择 AP，2PC 选择 CP。

常见错误 / 别踩这个坑

❌ 误用 2PC 于跨数据中心场景：网络延迟 + 协调者宕机 = 全系统阻塞。2PC 只适合同一数据中心的强一致需求。

❌ SAGA 忘记幂等补偿：补偿事务可能执行多次（网络重试）。每个补偿操作必须是幂等的。

❌ Outbox 不清理：Outbox 表会无限增长。���要在事件确认发出后及时删除或归档记录。

✅ 现实选择：Stripe 用 Outbox + Idempotency Keys；Uber 用 SAGA + Cadence/Temporal workflow engine（我们 Day 41 讨论过 Distributed Task Queue）。

深度连接：与之前内容的联系

  • Day 13 消息队列：SAGA 的编排依赖 Kafka/SQS 可靠传递
  • Day 38 支付系统：Stripe 使用幂等 Key + Outbox 保证支付事件不丢失
  • Day 47 Raft/Paxos：2PC 的协调者可以用 Raft 实现 HA
  • Day 63 分布式锁：SAGA 补偿期间需要锁防止并发冲突

🧒 ELI5

想象你和朋友合伙买礼物。2PC 是：你问所有人"有钱吗？"等大家都说有才付款，但如果你（协调人）突然失联，大家都傻等着。SAGA 是：每人先付自己那份，如果中途有人没钱，之前付了的人各自退款。Outbox 是：先把"我要给你发钱"这个承诺写在纸上压在枕头下，确保即使中途断网，这个承诺也不会丢。

#115 Distinct Subsequences [Hard] — 2-D Dynamic Programming (9/11)

🧩 二维动态规划模式 (9/11) — 延续 Day 149 (Interleaving String) 的模版

🔗 Links

  • LeetCode: https://leetcode.com/problems/distinct-subsequences/ 🔴 Hard
  • NeetCode: https://neetcode.io/problems/count-subsequences

现实类比 / Real-world Analogy

想象你在做文本搜索：给定一份长文档 s 和一个关键词 t，问关键词以子序列形式出现在文档里多少次（字符可以不连续，但顺序不变）。这就是 Distinct Subsequences 的核心——计算路径数量，而非判断是否存在。

问题定义

给定字符串 s 和 t，计算 s 的子序列中有多少个等于 t。

s = "rabbbit", t = "rabbit"
输出: 3
(三种方式选取 rabbit，对应三个不同的 'b' 被跳过)

映射到模版 / Map to Template

这是计数型 2D DP，不同于之前的：

  • Day 141 Edit Distance → 最小代价
  • Day 148 Target Sum → 组合计数（1D 背包）
  • Day 149 Interleaving String → 可行性判断

今天：dp[i][j] = s 的前 i 个字符中，t 的前 j 个字符作为子序列出现的次数。

转移规律（画表格找）：

"" r a b b i t ← t (j轴) "" 1 0 0 0 0 0 0 r 1 1 0 0 0 0 0 a 1 1 1 0 0 0 0 b 1 1 1 1 0 0 0 b 1 1 1 2 1 0 0 b 1 1 1 3 3 0 0 i 1 1 1 3 3 3 0 t 1 1 1 3 3 3 3 ← 答案!

规律：

  • s[i] == t[j]：既可以"用 s[i] 匹配 t[j]"(dp[i-1][j-1])，也可以"跳过 s[i]"(dp[i-1][j])

→ dp[i][j] = dp[i-1][j-1] + dp[i-1][j]

  • s[i] != t[j]：只能跳过 s[i]

→ dp[i][j] = dp[i-1][j]

Python 解法 + 执行追踪

def num_distinct(s: str, t: str) -> int:
    m, n = len(s), len(t)
    
    # dp[i][j] = count of t[:j] in s[:i] as subsequence
    dp = [[0] * (n + 1) for _ in range(m + 1)]
    
    # Base: empty t is a subsequence of any s prefix (1 way)
    for i in range(m + 1):
        dp[i][0] = 1
    
    for i in range(1, m + 1):
        for j in range(1, n + 1):
            # Always carry forward: skip s[i-1]
            dp[i][j] = dp[i-1][j]
            # If chars match, also add paths that USE s[i-1]
            if s[i-1] == t[j-1]:
                dp[i][j] += dp[i-1][j-1]
    
    return dp[m][n]

# Trace: s="rabbbit", t="rabbit"
# After filling: dp[7][6] = 3  ✓

空间优化（O(n) 滚动数组）：

def num_distinct_optimized(s: str, t: str) -> int:
    n = len(t)
    dp = [0] * (n + 1)
    dp[0] = 1  # empty t base case
    
    for ch in s:
        # Traverse RIGHT TO LEFT to avoid using updated values
        for j in range(n, 0, -1):
            if ch == t[j-1]:
                dp[j] += dp[j-1]
    
    return dp[n]

复杂度：Time O(m×n)，Space O(m×n) → 优化后 O(n)

举一反三 / Pattern Connections

题目DP 类型转移核心
Edit Distance (#72)最小代价min(insert, delete, replace)
Interleaving String (#97)可行性OR 操作
Distinct Subsequences (#115)计数加法累积
Burst Balloons (#312) ← 下一题区间 DP区间分割

关键区别：当 DP 问"有多少种方式"时，转移用加法；问"能否"时用OR；问"最优"时用min/max。

🗣️ 软技能 / Soft Skills — Day 153 (Synthesis)

Staff-Level Scenario: 你的团队欠了三年技术债，新 CTO 要求 6 个月内清零

场景设定

新 CTO 刚上任，宣布要在 Q2 结束前"清掉所有技术债"。你是 Staff Engineer，负责一个有 300 万行代码的核心服务，里面有未迁移的 Python 2 代码、循环依赖的模块、以及一堆没有测试的关键路径。你怎么做？

这道题综合了我们覆盖过的多个主题：技术债处理（Day 16）、优先级排序（Day 12）、向上管理（Day 3）、跨团队对齐（Day 14）。

STAR 框架拆解

Situation — 建立共同语言

技术债不是一个技术问题，它是一个沟通问题。先量化：

  • 把债务分类：安全风险 / 稳定性风险 / 开发速度阻碍
  • 用业务语言翻译："Python 2 EOL 意味着 CVE 无人修补"
  • 建立"债务登记册"（Debt Registry），每条记录关联业务影响

Task — 重新定义目标

❌ 坏目标："6 个月清零技术债"（不可能，会制造恐慌）

✅ 好目标："6 个月内消除 TOP 3 高风险债务，并建立不再累积新债的机制"

向 CTO push back，但要带数据和替代方案。

Action — 执行框架

Week 1-2: 审计 + 分级 → 高风险（安全/稳定性）: 立即行动 → 中风险（开发速度）: 季度计划 → 低风险（代码质量）: 随机结对处理 Month 1-2: 并行战略 → 新功能：50% 时间 → 技术债：30% 时间 (固定 budget, 不 cancel) → 防新债：20% 时间 (lint rules, PR 模版, ADR) Month 3-6: 进度可视化 → 每两周向 CTO 汇报：已消除的业务风险 (not "lines fixed") → 建立"债务燃烧图" Burndown Chart

Result — 预期成果

不要承诺"全部清零"，而是承诺：

  1. 安全债务：100% 消除（Python 2 迁移完成）
  2. 稳定性债务：关键路径测试覆盖率 >80%
  3. 流程：PR 中不引入新的 P0/P1 级债务

❌ 坏答案 vs ✅ 好答案

答法
❌"我们按 CTO 要求，全力以赴 6 个月冲刺清零！"
❌"技术债太多了，6 个月根本不可能，这个目标不合理。"
✅"我理解紧迫感。让我在这周做完审计，带着数据回来，我们一起定一个既能控风险又不停止业务交付的计划。"

Senior/Staff 加分点

  • 用 ADR (Architecture Decision Records) 防新债：每个架构决策留记录，避免同样的债务再犯
  • 把技术债变成可见资产：在 roadmap 上展示，让 PM 也参与优先级排序
  • 教团队识别债务：Code Review checklist 里加入"这会产生技术债吗？"

关键提炼

  1. 先审计后承诺：没有数据的计划是空谈
  2. 用业务语言：CTO 关心风险和速度，不关心代码行数
  3. 固定 budget，不 cancel：技术债时间被随意取消是债务积累的根源
  4. 建机制而非做一次性清理：真正的解法是不再产生新债
