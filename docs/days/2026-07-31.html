Q1: [💻 Algorithms — Graph BFS/DFS]

你在做 Walls and Gates（第104天）。给定一个二维网格，0 代表门，-1 代表墙，INF 代表空房间。如果从每个门同时开始BFS（多源BFS），和从每个空房间出发分别做BFS相比，为什么前者更优？

You're solving Walls and Gates (Day 104). The grid has 0 = gate, -1 = wall, INF = empty room. Why is multi-source BFS (start from all gates simultaneously) better than running BFS from each empty room separately?

<details><summary>显示答案 / Show Answer</summary>

多源BFS是最优解，因为：

  1. 时间复杂度：单源BFS对每个空房间跑一次 → O(rooms × M×N)，最坏 O(M²N²)。多源BFS只跑一次遍历 → O(M×N)。
  1. 核心洞察：把所有门同时加入队列，BFS天然保证每个格子第一次被访问时就是最短距离。门到空房间的距离 = BFS层数。
  1. Why it works: BFS explores level by level. When all gates start at level 0 simultaneously, the first time any empty room is reached, it's guaranteed to be the minimum distance from any gate — no room gets processed twice.
from collections import deque
def walls_and_gates(rooms):
    if not rooms: return
    m, n = len(rooms), len(rooms[0])
    INF = 2**31 - 1
    q = deque()
    for i in range(m):
        for j in range(n):
            if rooms[i][j] == 0:
                q.append((i, j))  # all gates at once
    while q:
        r, c = q.popleft()
        for dr, dc in [(0,1),(0,-1),(1,0),(-1,0)]:
            nr, nc = r+dr, c+dc
            if 0<=nr<m and 0<=nc<n and rooms[nr][nc]==INF:
                rooms[nr][nc] = rooms[r][c] + 1
                q.append((nr, nc))

结论 / Takeaway: 多源BFS = 把所有源点同时入队，相当于在源点外面虚拟加一层第0层。

</details>

Q2: [🐍 Python Craft — Caching & Serialization]

第101天学了缓存模式，第102天学了序列化。面试官问：你要缓存一个计算密集型函数的结果。你会选 functools.lru_cache、内存字典、还是 Redis？分别在什么场景下用？

Day 101 covered caching, Day 102 covered serialization. Interview question: You need to cache results of a compute-heavy function. When do you choose lru_cache vs in-memory dict vs Redis?

<details><summary>显示答案 / Show Answer</summary>

三种缓存方案的适用场景：

方案适用场景
@lru_cache同进程、纯函数、参数可哈希、单实例服务
dict cache需要手动控制过期（TTL）、或缓存复杂对象
Redis多进程/多实例、跨请求持久化、需要TTL/自动过期

Key decision framework:

  • Single process, pure function, immutable args → @lru_cache(maxsize=128) — zero overhead, built-in LRU eviction
  • Need TTL or custom eviction → dict + timestamp: cache[key] = (value, time.time())
  • Multi-instance or distributed → Redis: redis.setex(key, ttl, serialize(value))

序列化选择 (from Day 102):

  • Redis 存对象时：用 json.dumps (human-readable) 或 msgpack.dumps (compact, fast)
  • 不要用 pickle in Redis — security risk with untrusted data

面试金句: "lru_cache for in-process pure functions; Redis when you need shared state across processes or pods."

</details>

Q3: [🐍 Python Craft — Database Migrations]

第103天讲了Alembic和零停机迁移。面试官问：你要给一个有5000万行数据的PostgreSQL表加一个 NOT NULL 列，又不能停机，你怎么做？

Day 103 covered Alembic and zero-downtime migrations. Interview: You need to add a NOT NULL column to a 50M-row PostgreSQL table without downtime. Walk me through your approach.

<details><summary>显示答案 / Show Answer</summary>

零停机加 NOT NULL 列 — 3步法：

Step 1: Add column as nullable (无锁，秒级完成)

-- Fast: no table rewrite, no lock
ALTER TABLE users ADD COLUMN verified_at TIMESTAMPTZ;

Step 2: Backfill in batches (应用层/脚本，不锁表)

# Backfill 1000 rows at a time to avoid lock escalation
# PostgreSQL doesn't support UPDATE...LIMIT directly — use a subquery
BATCH = 1000
while True:
    updated = db.execute("""
        UPDATE users SET verified_at = created_at
        WHERE id IN (
            SELECT id FROM users
            WHERE verified_at IS NULL
            LIMIT :batch
        )
    """, {"batch": BATCH}).rowcount
    if updated == 0: break
    time.sleep(0.01)  # breathe between batches

Step 3: Add NOT NULL constraint + default (after backfill complete)

-- In Postgres 12+, this is nearly instant with a CHECK constraint trick
ALTER TABLE users
  ALTER COLUMN verified_at SET NOT NULL,
  ALTER COLUMN verified_at SET DEFAULT NOW();

Alembic 对应写法: 分3个migration文件，逐步部署。用 op.execute() 调用批量更新。

核心原则: 永远不要对大表做单步 ADD COLUMN NOT NULL DEFAULT — Postgres 12以前会锁全表重写！

面试金句: "Expand-contract pattern: first expand schema to be compatible with both old and new code, deploy new code, then contract by adding constraints."

</details>
