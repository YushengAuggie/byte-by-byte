🏗️ 系统设计 / System Design — Day 146 (Synthesis)

可观测性三支柱大综合：Metrics、Logs、Traces 的架构边界

Observability Three Pillars Deep Synthesis: When to Use Metrics vs Logs vs Traces

🔥 想象一下... / Real-World Scenario

凌晨 2 点，告警触发：checkout 服务 p99 延迟 > 5s。你是值班工程师，面对 200 个微服务。你的第一反应是什么？

It's 2 AM. Alert fires: checkout service p99 latency > 5s. You're on-call across 200 microservices. What do you reach for first?

这不是单一工具能回答的问题。可观测性的核心在于三支柱的协同，而不是各自为战。

🏗️ 架构图 / Architecture

用户请求 / User Request │ ▼ ┌─────────────────────────────────────────┐ │ API Gateway / Load Balancer │ └──────────────┬──────────────────────────┘ │ ┌──────────┼──────────┐ ▼ ▼ ▼ Checkout Payment Inventory Service Service Service │ │ │ └──────────┴──────────┘ │ ┌──────────┼──────────┐ ▼ ▼ ▼ METRICS LOGS TRACES (Prometheus)(ELK Stack)(Jaeger/Zipkin) │ │ │ └──────────┴──────────┘ │ ▼ Observability Platform (Datadog / Grafana / etc.)

🎯 三支柱的边界 / When to Use Each

📊 Metrics — WHEN something is wrong

特征 / Characteristics: 聚合数值、时间序列、低基数

用来 / Use for:

  • checkout_latency_p99 > 5s → 触发告警
  • CPU/内存利用率趋势
  • 请求速率、错误率（RED 方法：Rate, Error, Duration）
  • SLO/SLA 合规监控

不适合 / NOT for:

  • 高基数数据（每用户 ID、每订单 ID）→ 内存爆炸
  • 调试具体的一次失败请求
# ✅ Good: 低基数 / Low cardinality http_requests_total{method="POST", status="500"} 42 # ❌ Bad: 高基数 / High cardinality http_requests_total{user_id="u-82736", order_id="ord-99182"} 1 # → Prometheus 内存会爆 / This will OOM Prometheus

📋 Logs — WHAT happened

特征 / Characteristics: 结构化事件、任意上下文、可搜索

用来 / Use for:

  • "payment failed: card_declined, user_id=u-123, amount=99.99" → 具体根因
  • 审计日志（谁做了什么）
  • 错误堆栈信息
  • 业务事件流水

不适合 / NOT for:

  • 跨服务调用链路分析（你能看到 A 和 B 各自的日志，但不知道 A→B→C 这条链上哪里慢了）
  • 实时聚合计算（成本太高）
# ✅ 结构化日志 / Structured logging
logger.error("payment_failed", extra={
    "user_id": user.id,
    "amount": order.total,
    "reason": "card_declined",
    "trace_id": request.trace_id,  # ← 关键：关联 trace
})

🔍 Traces — WHERE in the distributed call chain

特征 / Characteristics: 分布式请求链路、跨服务 span、时序瀑布图

用来 / Use for:

  • 哪个服务最慢？(checkout → payment → bank API 哪段耗时最多)
  • 服务依赖关系可视化
  • 找出 fan-out 问题（1 个请求触发 50 个下游调用）

不适合 / NOT for:

  • 统计聚合告警（用 metrics 更高效）
  • 长期存储（trace 数据量大，通常采样 1%~10%）
Trace: order-checkout-82736 ├── [0ms] API Gateway 2ms ├── [2ms] checkout-service 450ms ← 瓶颈！ │ ├── [3ms] inventory-check 5ms │ ├── [8ms] payment-service 440ms ← 再查这里 │ │ ├── [9ms] fraud-check 2ms │ │ └── [11ms] bank-api 430ms ← 根因：外部 API 超时 │ └── [452ms] db-write 3ms └── [455ms] response 1ms

告警触发时的调查顺序 / Investigation order:

  1. Metrics → "哪个服务的哪个指标异常？"
  2. Traces → "这条请求链路哪一段最慢？"
  3. Logs → "那个具体的 span 里发生了什么？"

🚫 常见陷阱 / Common Mistakes

别踩这些坑 / Don't do this:

  1. 生产环境 DEBUG 日志全开 → 日志量×10，成本爆炸，降级到 WARN/ERROR
  2. 不传播 trace_id → 日志和 Trace 无法关联，根因分析断链
  3. Metrics 用高基数标签 → {user_id=xxx} 会让 Prometheus 内存 OOM
  4. 100% 采样 Trace → 每个请求都记录完整 Trace，存储成本不可接受
  5. 三者各自独立，不打通 → 看 metrics 发现问题，但日志里没有 trace_id，无法关联

🛠️ 黄金标准实践 / Golden Standard

告警规则 (Metrics) → SLO Dashboard ↓ 触发调查 (Trace ID from log) ↓ Trace 瀑布图定位慢 span ↓ 跳到该 span 的 Logs ↓ 根因：外部 API 超时

工具链推荐 / Toolchain:

  • Open source: Prometheus + Loki + Tempo (Grafana 三件套, 同一 trace_id 互通)
  • SaaS: Datadog (三合一, 最贵) / New Relic / Honeycomb (trace-first)

  2. OpenTelemetry — The Standard
  3. Honeycomb: Observability vs Monitoring

🧒 ELI5

想象你家的电力系统：

  • Metrics = 电表（告诉你用了多少度电，啥时候用电量突然飙升）
  • Logs = 用电记录本（"晚上8点，微波炉用了600W，空调用了1200W"）
  • Traces = 电路图（帮你找到哪根线路跳闸了导致厨房停电）

三个都要，缺一不可。

💻 算法 / Algorithms — Day 146

#309 Best Time to Buy and Sell Stock with Cooldown (Medium) — 2-D Dynamic Programming

🧩 二维动态规划 (3/11) — 在 Day 143 模版基础上继续

Building on the 2-D DP template from Day 143

今天这题看起来像 1-D DP（只有一个数组 prices），但它实际上是一个状态机 DP — 每个时间点有多个"状态维度"，本质是二维的。

🎯 问题 / Problem

🔗 LeetCode #309 🟡 Medium

📹 NeetCode

给你一个价格数组，每次卖出后必须冷静一天（不能买入）。求最大利润。

Given prices array; after selling, you must wait 1 day before buying again. Maximize profit.

Input: prices = [1, 2, 3, 0, 2]
Output: 3
Explanation: Buy on day 0 (price=1), sell on day 1 (price=2),
             cooldown on day 2, buy on day 3 (price=0), sell on day 4 (price=2)

🔗 映射到模版 / Mapping to Pattern

二维DP的本质：dp[i][state]，其中：

  • i = 第 i 天
  • state = 当前状态 (3种)
状态机 / State Machine: HOLDING ──sell──→ SOLD ↑ │ buy cooldown │ ↓ IDLE ←──────── COOLDOWN

三个状态 / Three States:

  • HOLDING: 持有股票中
  • SOLD: 刚卖出（下一天必须进入 COOLDOWN）
  • IDLE: 空仓且不在冷静期（可以买入）

🐍 Python Solution with Trace

from typing import List

def maxProfit(prices: List[int]) -> int:
    # State machine DP
    # holding = max profit while holding stock
    # sold    = max profit on day we just sold
    # idle    = max profit while not holding, not in cooldown
    
    holding = -prices[0]  # bought on day 0
    sold = 0              # can't have sold on day 0
    idle = 0              # started idle
    
    for price in prices[1:]:
        prev_holding = holding
        prev_sold = sold
        prev_idle = idle
        
        # Today I'm holding: either I was already holding,
        # or I was idle yesterday and bought today
        holding = max(prev_holding, prev_idle - price)
        
        # Today I just sold: I was holding and sold today
        sold = prev_holding + price
        
        # Today I'm idle: I was idle, or I was in cooldown (just sold yesterday)
        idle = max(prev_idle, prev_sold)
    
    # Can't end while holding → max of sold or idle
    return max(sold, idle)

手动追踪 / Manual Trace prices = [1, 2, 3, 0, 2]:

Day 0 (price=1): holding=-1, sold=0, idle=0 Day 1 (price=2): holding=max(-1, 0-2)=-1 sold =max(-1+2)=1 idle =max(0, 0)=0 Day 2 (price=3): holding=max(-1, 0-3)=-1 sold =max(-1+3)=2 idle =max(0, 1)=1 Day 3 (price=0): holding=max(-1, 1-0)=1 ← 冷静完买入! sold =max(-1+0)=-1 idle =max(1, 2)=2 Day 4 (price=2): holding=max(1, 2-2)=1 sold =max(1+2)=3 ← 最终卖出 idle =max(2, -1)=2 Result: max(sold=3, idle=2) = 3 ✅

复杂度 / Complexity:

  • Time: O(n)
  • Space: O(1) — 只用三个变量！

🧩 与模版的区别 / Difference from Template

经典二维 DP 模版（LCS、网格路径）用 dp[i][j] 二维数组。

这道题的"第二维"是状态而不是第二个序列 — 状态空间被压缩成了 3 个变量。这是 2-D DP 的一个重要变体：状态机 DP。

经典 2D DP:     dp[i][j] = f(dp[i-1][j], dp[i][j-1], ...)
状态机 DP:      dp[i][state] = f(dp[i-1][other_states])
这道题:         holding/sold/idle = f(prev_holding/sold/idle, price)

Fresh Senior/Staff Scenario: 跨职能系统重构的利益相关者管理

Cross-Functional System Rewrite: Stakeholder Alignment at Staff Level

🎯 今日场景 / Today's Scenario

"你发现公司核心支付服务是 10 年前的老代码，技术债严重，已经影响到新功能交付速度和稳定性。但 PM 说 Q4 必须上线 3 个大功能，CFO 不想批预算做'看不见的工作'，你的团队已经精疲力竭。作为 Staff Engineer，你会怎么做？"
"You discover the core payment service is 10-year-old legacy code with severe tech debt impacting feature velocity and stability. PM says 3 major features must ship in Q4, CFO won't fund 'invisible work,' and your team is burned out. As Staff Engineer, what do you do?"

⭐ STAR Framework

Situation — 诊断清楚再开口

先量化，不要凭感觉 / Quantify before you speak:

  • "过去 6 个月，支付服务相关 incident 导致了 47 小时工程师 on-call 时间"
  • "新功能平均开发周期从 Q1 的 2 周增加到 Q3 的 5 周，其中 60% 时间花在绕过老系统"
  • "上季度有 2 次 P1 故障，各自造成约 $X 营收损失"

核心原则：把技术债翻译成业务语言

If you say "the code is unmaintainable," nobody cares.

If you say "tech debt cost us $800K in lost velocity and incidents last quarter," now you have attention.

Task — 你的实际目标是什么

不是"重构代码"（这是手段）。

真正的目标：

  1. 恢复特性交付速度（PM 关心）
  2. 降低系统风险（CTO/CFO 关心）
  3. 保护团队，避免更多流失（EM/CPO 关心）

Staff 思维 / Staff-level framing: 你的 job 不是写代码，是让整个系统（包括人和技术）更健康。

Action — 具体做了什么

Step 1: 建立"技术债成本模型"

季度技术债成本 =
  直接成本: incident 小时数 × 工程师时薪 + 营收损失
+ 机会成本: 特性延迟交付 × 商业价值
+ 风险成本: 估算下次 P1 概率 × 潜在损失

Step 2: 提出"扼杀者无花果"策略（Strangler Fig Pattern）

不是推倒重来（风险太高），而是：

  • 在新服务旁边构建，逐步迁移流量
  • 每个 sprint 同时交付业务功能 + 迁移旧模块的一部分
  • 向 PM 展示：新架构部分的特性开发速度已经快了 3 倍

Step 3: 利益对齐 / Stakeholder alignment

角色他们关心的你的说法
PM功能交付"重构第 1 个模块后，后续功能开发快 3x"
CFOROI"投入 6 人月，换回每季度节省 $X 工程成本"
CTO风险"不动的话，下次 P1 概率从 15% 升到 40%"
团队不再痛苦"我们会逐步减少 on-call 负担"

Step 4: 提供两个选项，不是一个

❌ 坏做法："我们必须重构，需要 6 个月"

✅ 好做法：

  • 选项 A (推荐): 20% 时间持续重构 + 正常功能交付。6 个月内迁移 80%，第 3 个月起速度提升可见
  • 选项 B (保守): 只修最关键的稳定性问题。Q4 功能按时交付，但技术债继续累积，明年再评估

给 leadership 选择权，他们更容易接受你的推荐方案。

Result — 结果和学到的

  • Q4 功能按时交付 ✅（给了 PM 他们想要的）
  • 同时完成 30% 旧系统迁移 ✅
  • Incident 率下降 40%，on-call 时间减半 ✅
  • 团队 engagement 改善（有进展感，不再是纯救火）✅

❌ 坏 vs ✅ 好

❌ 工程师思维:

"老代码太烂了，我们需要 6 个月全面重写，不然我要辞职了。"

✅ Staff 思维:

"我做了一个分析，当前技术债每季度让我们损失约 X。我有两个方案给你——我推荐方案 A，因为它在最小化 Q4 风险的同时开始偿还债务。能给我 30 分钟走一遍这个分析吗？"

🔑 Senior/Staff 关键洞察 / Key Takeaways

  1. 量化一切 — 技术问题不说业务语言，就等于在说方言
  2. 扼杀者无花果优于大爆炸重写 — 持续交付价值，降低风险
  3. 给选项，不给命令 — 让 stakeholder 感觉他们在决策
  4. 对齐激励 — 每个角色的痛点不同，说他们听得懂的话
  5. 用数据推动，不用情绪 — "我们很痛苦" < "上季度损失了 $X"

🔬 深度综合：混合检索架构 + 状态记忆 / Deep Synthesis

覆盖了 30 个 AI 概念之后，来综合两个之前分开讲过的主题：RAG（Day 16）+ 向量数据库（Day 18）+ 推理优化（Day 46）。

# pip install openai faiss-cpu numpy

import openai
import faiss
import numpy as np
from typing import Optional

class ProductionRAGSystem:
    """
    Production-grade RAG: vector search + KV cache awareness + streaming
    Synthesizes: Embeddings + Vector DB + Inference Optimization
    """
    
    def __init__(self, dimension: int = 1536):
        # FAISS index — in production: use Pinecone/Weaviate/pgvector
        self.index = faiss.IndexFlatIP(dimension)  # Inner product (cosine sim)
        self.documents: list[str] = []
        self.client = openai.OpenAI()
    
    def embed(self, text: str) -> np.ndarray:
        response = self.client.embeddings.create(
            model="text-embedding-3-small",
            input=text
        )
        vec = np.array(response.data[0].embedding, dtype=np.float32)
        # Normalize for cosine similarity
        return vec / np.linalg.norm(vec)
    
    def add_documents(self, docs: list[str]) -> None:
        for doc in docs:
            vec = self.embed(doc)
            self.index.add(vec.reshape(1, -1))
            self.documents.append(doc)
    
    def retrieve(self, query: str, k: int = 3) -> list[str]:
        query_vec = self.embed(query)
        distances, indices = self.index.search(query_vec.reshape(1, -1), k)
        return [self.documents[i] for i in indices[0] if i < len(self.documents)]
    
    def answer(self, question: str) -> str:
        # Step 1: Retrieve relevant context
        contexts = self.retrieve(question)
        context_str = "\n\n".join(f"[{i+1}] {c}" for i, c in enumerate(contexts))
        
        # Step 2: Generate with streaming (reduces perceived latency)
        # KV cache: system prompt stays hot in cache → cheaper repeated calls
        stream = self.client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[
                {"role": "system", "content": "Answer using only the provided context."},
                {"role": "user", "content": f"Context:\n{context_str}\n\nQuestion: {question}"}
            ],
            stream=True  # streaming for UX
        )
        
        result = ""
        for chunk in stream:
            delta = chunk.choices[0].delta.content or ""
            result += delta
            print(delta, end="", flush=True)  # stream to user
        return result

# Usage
rag = ProductionRAGSystem()
rag.add_documents([
    "Python asyncio uses epoll on Linux for I/O multiplexing.",
    "The GIL prevents true parallelism for CPU-bound tasks.",
    "ProcessPoolExecutor bypasses the GIL using separate processes.",
])
answer = rag.answer("How does Python handle concurrent I/O?")
