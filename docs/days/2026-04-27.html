主题 / Topic: Design Google Maps

难度 / Difficulty: Advanced | 阶段 / Phase: Mastery

预计阅读 / Read time: ~3 分钟

🌍 想象你在设计 Google Maps...

你需要支持 10亿用户 实时导航、路线规划、地图渲染，还要处理交通状况更新。

You need to support 1B users doing real-time navigation, route planning, map rendering, and live traffic updates.

这不只是"存地图数据"那么简单——挑战在于数据量庞大、实时性要求高、以及地理空间查询的复杂性。

It's not just "store map data" — the challenge is massive data volume, real-time requirements, and complex geospatial queries.

🔑 核心设计决策 / Key Design Decisions

1. 地图瓦片系统 / Map Tile System

地图按 Mercator 投影 切割为 256×256 瓦片，按 zoom level (0-20) 分层存储。

Maps are sliced into 256×256 tiles using Mercator projection, stored per zoom level.

Zoom 0 = 1 tile (whole world)
Zoom 10 = 1M tiles (city level)
Zoom 18 = 68B tiles (street level)

存储策略 / Storage: S3 + CloudFront CDN

瓦片是静态资源，CDN 命中率 >95%，极大减少源服务器压力。

Tiles are static assets — >95% CDN hit rate massively reduces origin load.

2. 路线规划 / Routing Engine

使用 Dijkstra / A\* 算法，但直接跑整个地图不现实（节点太多）。

Pure Dijkstra on the full map is infeasible (too many nodes).

解决方案 / Solution: Hierarchical Routing (CH — Contraction Hierarchies)

Level 3: Highways (interstate) ← 长途优先走这层 Level 2: Major roads (city) ← 城际 Level 1: Local streets ← 最后一公里

先在高层图快速找大方向，再在低层补充细节——搜索空间缩小 1000x。

Search at high levels for direction, detail at low levels — 1000x smaller search space.

3. 实时交通 / Real-Time Traffic

数据来源 / Sources:

  • 匿名 GPS 轨迹（手机上报）/ Anonymous GPS traces from phones
  • 事故/施工报告 / Incident reports
  • 历史交通模式 / Historical traffic patterns

架构:

GPS probes → Kafka → Stream Processor → Edge Weight Updates → Route Re-calculation

每条路的"边权重"代表当前行驶时间，每 1-5 分钟更新一次。

Each road edge weight = current travel time, updated every 1-5 min.

4. 地理索引 / Geo-Spatial Indexing

搜索"附近的星巴克"需要高效的地理查询。

"Find Starbucks nearby" needs efficient geo queries.

方案 / Approach: Geohash + R-Tree (PostGIS)

⚠️ 别踩这个坑 / Common Mistakes

❌ 坑 1: 把路线规划做成单体服务

路线计算 CPU 密集，必须独立扩展。

Route computation is CPU-heavy — must scale independently.

❌ 坑 2: 忽略地图数据更新

路网每天都在变（新路、施工），需要 ETL pipeline 定期从 OpenStreetMap 导入。

Road networks change daily — need ETL from OpenStreetMap.

❌ 坑 3: 以为实时交通只需要快速存储

真正的挑战是 数据新鲜度 vs 系统负载 的权衡——更新太频繁会压垮路由服务。

Real challenge is freshness vs load — too-frequent updates overwhelm routing.

什么时候用 / When to Use

当你看到这些信号时，考虑二分搜索：

Look for these signals to reach for binary search:

  • 排序数组 里找某个值
  • 要求 O(log n) 时间复杂度
  • 找 "满足条件的最小/最大值"（最小化/最大化）
  • 搜索空间可以 单调地判断 True/False

识别信号 / Signals

sorted array, search, O(log n),
"find minimum that satisfies condition",
"find maximum", monotonic property

通用模版 / Template

def binary_search(arr, target):
    left, right = 0, len(arr) - 1
    
    while left <= right:
        mid = (left + right) // 2  # 避免溢出：left + (right - left) // 2
        
        if arr[mid] == target:
            return mid
        elif arr[mid] < target:
            left = mid + 1   # target 在右半边
        else:
            right = mid - 1  # target 在左半边
    
    return -1  # not found

Time: O(log n) | Space: O(1)

核心洞察 / Key Insight

每次排除一半搜索空间 — 不只用于排序数组，任何单调性都可以二分。
Each step eliminates half the search space — works for any monotonic property, not just sorted arrays.

Input: nums = [-1, 0, 3, 5, 9, 12], target = 2

🗺️ 套用模版 / Map to Template

这就是模版的原型题 — 直接套用即可！

This IS the template — apply it directly!

def search(nums: list[int], target: int) -> int:
    left, right = 0, len(nums) - 1
    
    while left <= right:
        mid = (left + right) // 2
        
        if nums[mid] == target:
            return mid
        elif nums[mid] < target:
            left = mid + 1   # target must be to the right
        else:
            right = mid - 1  # target must be to the left
    
    return -1

🔬 执行追踪 / Trace

nums = [-1, 0, 3, 5, 9, 12], target = 9 Iteration 1: left=0, right=5, mid=2 → nums[2]=3 < 9 → left=3 Iteration 2: left=3, right=5, mid=4 → nums[4]=9 == 9 → return 4 ✅ nums = [-1, 0, 3, 5, 9, 12], target = 2 Iteration 1: left=0, right=5, mid=2 → nums[2]=3 > 2 → right=1 Iteration 2: left=0, right=1, mid=0 → nums[0]=-1 < 2 → left=1 Iteration 3: left=1, right=1, mid=1 → nums[1]=0 < 2 → left=2 left(2) > right(1) → return -1 ✅

🎨 前端 / Frontend — Day 32

主题 / Topic: Debounce & Throttle — Implement from Scratch

类别 / Category: JavaScript Core

预计阅读 / Read time: ~2 分钟

🌍 真实场景 / Real-World Scenario

你在做一个 dashboard，需要实现一个搜索框。用户每敲一个字母，就会发一次 API 请求。

You're building a dashboard with a search box. Every time the user types a letter, it fires an API request.

如果用户快速输入 "apple"，系统会发送 5 次请求（a, ap, app, appl, apple）。这会浪费服务器资源，甚至导致竞态条件（先发的请求后返回，覆盖了最终结果）。

If the user types "apple" quickly, it sends 5 requests. This wastes server resources and can cause race conditions (an earlier request returns later and overwrites the final result).

解决方案：防抖 (Debounce) 和 节流 (Throttle)。

Solution: Debounce and Throttle.

💻 代码实现 / Code Snippets

1. 防抖 (Debounce)

概念： 动作停止后，等待 N 毫秒再执行。如果期间又触发了，重新计时。

Concept: Wait N ms after the last action before executing. If triggered again, reset the timer.

场景： 搜索框自动补全、窗口 resize。

Use case: Search autocomplete, window resize.

function debounce<T extends (...args: any[]) => void>(
  func: T, 
  wait: number
): (...args: Parameters<T>) => void {
  let timeoutId: ReturnType<typeof setTimeout> | null = null;
  
  return function(this: any, ...args: Parameters<T>) {
    // 如果已经有定时器，清除它（重新计时）
    // If there's an existing timer, clear it (reset)
    if (timeoutId) {
      clearTimeout(timeoutId);
    }
    
    // 设置新的定时器
    // Set a new timer
    timeoutId = setTimeout(() => {
      func.apply(this, args);
    }, wait);
  };
}

// 用法 / Usage:
const search = debounce((query: string) => fetchAPI(query), 300);
// 快速输入 "apple" 只会在停顿 300ms 后触发一次 fetchAPI("apple")

2. 节流 (Throttle)

概念： 规定时间内，最多只执行一次。不管触发多少次，按固定频率执行。

Concept: Execute at most once every N ms, ensuring a steady rate of execution regardless of how many times it's triggered.

场景： 滚动事件 (scroll) 监听、按钮防连击。

Use case: Scroll event listeners, preventing double-clicks on buttons.

function throttle<T extends (...args: any[]) => void>(
  func: T, 
  limit: number
): (...args: Parameters<T>) => void {
  let inThrottle: boolean = false;
  
  return function(this: any, ...args: Parameters<T>) {
    if (!inThrottle) {
      func.apply(this, args);
      inThrottle = true;
      
      // 限制时间内不允许再次执行
      // Prevent execution until limit passes
      setTimeout(() => {
        inThrottle = false;
      }, limit);
    }
  };
}

// 用法 / Usage:
const handleScroll = throttle(() => checkScrollPosition(), 100);
// 疯狂滚动时，每 100ms 最多执行一次 checkScrollPosition

解析：<br>

⚖️ 何时使用 / When to use

  • Debounce: 当你只关心最终状态时（如用户打完字了、窗口拉完了）。
  • Throttle: 当你需要持续的中间状态时（如页面滚动过程中需要不断更新进度条，但不能太频繁）。

防抖（Debounce）就像电梯关门：只要有人进电梯，门就会重新等 5 秒才关。如果一直有人进，门就一直不关，直到最后一个人进来后等够 5 秒。

主题 / Topic: Function Calling & Tool Use in LLMs

类别 / Category: Practical | 阶段 / Phase: Mastery

预计阅读 / Read time: ~2 分钟

🧠 直观理解 / Intuitive Explanation

LLM（大语言模型）就像一个被锁在没有网的房间里的超级大脑。它知道很多东西，但无法知道今天的天气，也无法帮你发邮件。

An LLM is like a super-brain locked in a room without internet. It knows a lot, but it can't check today's weather or send an email for you.

Function Calling (函数调用) 就是给这个大脑递纸条的机制。

Function Calling is the mechanism to pass notes to this brain.

你告诉 LLM："我这里有几个工具（函数），比如 get_weather(city) 和 send_email(to, body)。如果你需要，告诉我你要用哪个工具，以及参数是什么。"

You tell the LLM: "I have tools like get_weather(city) and send_email(to, body). If you need them, tell me which one to use and what the arguments are."

当用户问："今天西雅图天气如何？"

When a user asks: "What's the weather in Seattle today?"

LLM 不会瞎编，而是返回一个结构化的 JSON：

The LLM won't hallucinate. Instead, it returns structured JSON:

{"name": "get_weather", "arguments": {"city": "Seattle"}}

你的代码拿到这个 JSON，去真正调用天气 API，然后把结果（比如 "15°C, 阴天"）再喂给 LLM。LLM 最后生成人类语言："今天西雅图是阴天，气温约 15°C。"

Your code takes this JSON, actually calls the weather API, and feeds the result ("15°C, cloudy") back to the LLM. The LLM then generates human text: "It's cloudy in Seattle today, around 15°C."

⚙️ 它是如何工作的 / How it Works

  1. 定义工具 (Define Tools): 在 API 请求中，用 JSON Schema 描述你的函数。
  2. 模型决定 (Model Decides): 模型判断是否需要调用工具。如果需要，它会暂停生成文本，转而生成一个函数调用请求（Tool Call）。
  3. 执行函数 (Execute Function): 你的应用程序（不是模型！）执行实际的代码。
  4. 返回结果 (Return Result): 将函数执行结果作为 tool_message 追加到对话历史中，再次请求模型。
  5. 最终回答 (Final Answer): 模型根据函数结果生成最终回答。

🚀 应用场景 / Applications

  • 联网搜索: 让模型能搜索最新资讯 (如 Perplexity, ChatGPT 联网版)。
  • 操作数据库: 将自然语言转换为 SQL 查询并执行。
  • 自动化办公: 读取日历、发送邮件、创建 Jira ticket。
  • Agent 核心: 这是所有 AI Agent（智能体）能"行动"的基础。

💻 运行示例 / Runnable Python Snippet

我们需要 openai 库。

We need the openai library.

import os
import json
from openai import OpenAI

# 确保设置了 OPENAI_API_KEY 环境变量
# Ensure OPENAI_API_KEY is set
client = OpenAI(api_key=os.environ.get("OPENAI_API_KEY"))

# 1. 定义我们的工具 (假装这是一个真实的天气 API)
# Define our tool (pretend this is a real weather API)
def get_current_weather(location):
    """Get the current weather in a given location"""
    if "tokyo" in location.lower():
        return json.dumps({"location": "Tokyo", "temperature": "10", "unit": "celsius"})
    elif "san francisco" in location.lower():
        return json.dumps({"location": "San Francisco", "temperature": "72", "unit": "fahrenheit"})
    else:
        return json.dumps({"location": location, "temperature": "unknown"})

# 2. 告诉模型我们有什么工具
# Tell the model what tools we have
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_current_weather",
            "description": "Get the current weather in a given location",
            "parameters": {
                "type": "object",
                "properties": {
                    "location": {
                        "type": "string",
                        "description": "The city and state, e.g. San Francisco, CA",
                    },
                },
                "required": ["location"],
            },
        },
    }
]

messages = [{"role": "user", "content": "What's the weather like in San Francisco?"}]

# 3. 第一次请求：模型决定调用工具
# First request: Model decides to call the tool
response = client.chat.completions.create(
    model="gpt-3.5-turbo",
    messages=messages,
    tools=tools,
    tool_choice="auto",  # auto is default
)
response_message = response.choices[0].message
tool_calls = response_message.tool_calls

if tool_calls:
    # 4. 执行函数并返回结果
    # Execute function and return result
    messages.append(response_message)  # 把模型的调用请求加进去
    
    for tool_call in tool_calls:
        function_name = tool_call.function.name
        function_args = json.loads(tool_call.function.arguments)
        
        if function_name == "get_current_weather":
            function_response = get_current_weather(location=function_args.get("location"))
            
            messages.append(
                {
                    "tool_call_id": tool_call.id,
                    "role": "tool",
                    "name": function_name,
                    "content": function_response,
                }
            )
            
    # 5. 第二次请求：模型根据结果生成最终回答
    # Second request: Model generates final answer based on result
    second_response = client.chat.completions.create(
        model="gpt-3.5-turbo",
        messages=messages,
    )
    print(second_response.choices[0].message.content)
    # Output: The weather in San Francisco is currently 72 degrees Fahrenheit.

🧒 ELI5

想象你是一个被关在房间里的聪明人，有人在门外问你问题。如果问题是"1+1等于几"，你可以直接回答。如果问题是"今天外面下雨了吗"，你不知道。但是，门外的人给了你一个对讲机（Function Calling），你可以用对讲机呼叫"天气预报员"，问他外面的天气，然后再把答案告诉门外的人。模型本身不执行代码，它只是告诉你"请帮我运行这段代码"。
