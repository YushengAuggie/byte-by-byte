🏗️ 系统设计 / System Design — Day 159 (Synthesis)

主题 / Topic: Event Sourcing + CQRS：把分布式系统所有经验串起来

想象你在设计一个金融交易系统...

传统做法：用户下单 → UPDATE orders SET status='paid' WHERE id=X。

问题是：你永远不知道"发生过什么"，只知道"现在是什么"。

这就是为什么 Stripe、Shopify、Uber 都用 Event Sourcing。

核心思想 / Core Concepts

Event Sourcing（事件溯源）：不存储当前状态，存储每一个事件（发生了什么）。

❌ 传统：orders table { id, status="paid", amount=100 } ✅ ES：events table { order_created, payment_initiated, payment_confirmed } → 当前状态 = replay(所有事件)

CQRS（命令查询职责分离）：写操作（Command）和读操作（Query）走不同的路径。

为什么这样设计？/ Key Tradeoffs

优势 Pros劣势 Cons
完整审计日志（金融合规必备）读取需要 replay，要维护 Read Model
时间旅行：可以回放到任意时间点最终一致性，读写有延迟
解耦：事件驱动，微服务天然解耦Event schema 变更很难（不可变事件）
读写独立扩展学习曲线陡，调试复杂

这正好串联了我们学过的所有主题：

  • Kafka（消息队列 Day 13）→ 事件总线
  • Redis（分布式缓存 Day 39）→ Read Model 加速
  • Elasticsearch（搜索引擎 Day 29）→ 复杂查询 Read Model
  • 最终一致性（CAP 定理 Day 12）→ 命令/查询延迟
  • Snapshot → 类似数据库检查点

别踩这个坑 / Common Mistakes

坑 1：事件太粗粒度

❌ UserUpdated { all_fields... }  # 什么都改了？
✅ UserEmailChanged { old, new }
   UserAddressUpdated { address }

坑 2：在事件里存业务逻辑

❌ event: { discount_applied: true, final_price: 90 }  # 价格逻辑变了就麻烦
✅ event: { coupon_code: "SAVE10" }  # 在 replay 时重新计算

坑 3：忘记 Idempotency

事件可能被消费多次（Kafka at-least-once），处理器必须幂等。

什么时候用 / When to Use

✅ 金融/支付系统（Stripe）

✅ 电商订单（Shopify）

✅ 协作编辑（Google Docs — Operational Transform 是变种）

✅ 游戏状态（每帧 = 一个事件）

❌ 简单 CRUD 应用（杀鸡用牛刀）

❌ 读多写少且不需要历史（用普通缓存更简单）

🧒 ELI5

想象你的银行不存"余额=1000元"，而是存"存了500、花了200、存了700..."的流水账。要知道余额，就把所有账单加起来。这样你永远能查到任何一天的余额，也能知道每笔钱怎么来的。Event Sourcing 就是这个思路。

💻 算法 / Algorithms — Day 159

题目 / Problem: #55 Jump Game (Medium) — Greedy

模式位置 / Pattern: 🧩 贪心模式 (2/8) — building on the template from Day 158

🧩 贪心模式 (2/8) — 延续昨天的模版

昨天 #53 Maximum Subarray 用了贪心思路（局部最优 → 全局最优）。
今天 Jump Game 是同一模式的经典变种：维护一个"能到达的最远位置"。

关键区别 vs 昨天：

  • Maximum Subarray：维护"当前子数组和"，负了就重置
  • Jump Game：维护"最远可达 index"，扫描时不断更新

🔗 链接

  • LeetCode: https://leetcode.com/problems/jump-game/ 🟡 Medium
  • NeetCode: https://neetcode.io/problems/jump-game

现实类比 / Real-World Analogy

想象你在过一条河，河上有很多石头。每块石头上写了一个数字，表示"从这块石头最多能跳多远"。

[2, 3, 1, 1, 4] 0 1 2 3 4 ← index

站在 index 0（数字 2）→ 最远能跳到 index 2

站在 index 1（数字 3）→ 最远能跳到 index 4

只要 index 4（终点）在你的"最远可达"范围内，你就能过河。

问题描述

给定整数数组 nums，nums[i] 表示在位置 i 最多可以跳的步数。

初始在 nums[0]，判断是否能到达最后一个下标。

Input: nums = [2,3,1,1,4] → Output: True Input: nums = [3,2,1,0,4] → Output: False (永远到不了 index 4)

映射到贪心模版

# 通用贪心模版：维护局部最优量，遍历更新
# 这里的"局部最优量" = 当前能到达的最远 index

def canJump(nums: list[int]) -> bool:
    max_reach = 0  # 当前能到达的最远位置
    
    for i in range(len(nums)):
        if i > max_reach:
            # 当前位置已经超出可达范围，死路
            return False
        # 贪心：从 i 出发，最远能到哪？
        max_reach = max(max_reach, i + nums[i])
    
    return True

执行轨迹 / Trace (nums = [2,3,1,1,4]):

i=0: max_reach = max(0, 0+2) = 2 i=1: max_reach = max(2, 1+3) = 4 i=2: max_reach = max(4, 2+1) = 4 i=3: max_reach = max(4, 3+1) = 4 i=4: max_reach = max(4, 4+4) = 8 → 返回 True ✅

失败案例 (nums = [3,2,1,0,4]):

i=0: max_reach = 3 i=1: max_reach = 3 i=2: max_reach = 3 i=3: max_reach = max(3, 3+0) = 3 i=4: i(4) > max_reach(3) → 返回 False ✅

为什么贪心正确？/ Proof of Correctness

贪心的难点不是写代码，是证明策略正确。

直觉：如果我们能到达位置 i，就一定能到达 0..i 之间任意位置（因为可以"停短一点"）。

因此，max_reach 是所有可达位置中最优的选择——不需要枚举所有路径。

反证法：假设贪心失败（认为不可达），但真实可达。那么必然存在某个位置 j < max_reach 能跳得更远——但我们已经用 max 取了所有位置的最远值，矛盾。✅

复杂度 / Complexity

  • 时间：O(n) — 一次遍历
  • 空间：O(1) — 只用一个变量

vs 暴力 DFS/BFS：O(n²)，贪心完胜

举一反三 / Pattern Connections

🧒 ELI5

你在玩一个跳格子游戏，每个格子写着"最多跳几步"。你不需要想最优路线，只需要记住你目前最远能跳到哪。每走到一格，就更新这个最远距离。如果走着走着发现自己的位置已经超过了最远距离，就说明你"卡住了"，到不了终点。

🗣️ 软技能 / Soft Skills — Day 159 (Synthesis)

场景 / Scenario: 上线前一周发现根本性设计缺陷——Staff Engineer 的关键时刻

为什么这个场景重要

这不是"有没有犯过错"的问题，是"你在极端压力下如何做决策和沟通"。

Senior/Staff 面试官想看的：你会不会掩盖问题？遇到 bad news 能不能直接说？

场景设定

"你的团队花了 5 个月构建了一个新的订单处理系统，计划下周上线。你在最后一次压测中发现，当并发超过 500 TPS 时，系统会出现数据不一致——根本原因是当初的分布式锁设计有漏洞，修复需要 3-4 周。你会怎么做？"

STAR 拆解

Situation（情况）

"我们的支付结算系统计划在双十一前上线，距离上线剩 8 天。在最后一轮压测时，我发现在 600 TPS 峰值下，约 0.3% 的交易会出现重复扣款，原因是 Redis 分布式锁的 expire 时间在某些网络抖动情况下会失效。"

Task（任务）

"我需要在极短时间内：(1) 评估风险和修复路径，(2) 决定是否推迟上线，(3) 向 PM、CTO 和业务方沟通。"

Action（行动）— 这里是重点

立刻做的事（前 2 小时）：

  1. 不要自己扛：马上告诉 tech lead 和 PM，不要等到"我再确认一下"
  2. 量化风险：0.3% at 600 TPS = 1.8 笔/秒异常，一天 155,000 笔错误交易——不可接受
  3. 提出选项，不是问题：

- Option A：推迟 3 周彻底修复（质量最高，损失时机）

- Option B：上线但限流在 200 TPS，问题不出现，2 周内补丁 （有限功能上线）

- Option C：上线时加补偿事务层（对账任务），接受少量错误并修复 （最激进）

  1. 给推荐：我推荐 Option B，附上风险评估文档，让决策者决定

沟通方式：

"发现 bug 的当天，我写了一个 1-page 的 Risk Doc：问题描述、影响范围、3 个选项的 pros/cons，以及我的推荐。直接发给 PM、Engineering Manager 和 CTO，标题写 '[需要决策] 支付系统上线风险评估'。"

Result（结果）

"决定了 Option B（限流上线）。我们在 2 周内发布了完整修复，没有发生任何生产事故。事后 PM 说，最让他信任的不是我们解决了问题，而是我们在第一时间就报告了问题。"

❌ Bad vs ✅ Good

❌ 危险回答：

"我加班加点，3 天把它修了，没有推迟上线。" — 听起来厉害，实则红旗：你掩盖了风险。

✅ 强回答的关键：

  1. 第一时间透明汇报，不等到"有把握了再说"
  2. 带着选项和推荐去谈，不是带着问题
  3. 量化影响（数字说话）
  4. 决策后 100% 执行，不二次质疑

Senior/Staff 加分项

"我后来把这个场景写进了 team 的 on-call runbook 和 design review checklist，确保以后每个分布式锁设计都要覆盖 network partition 场景。"

把个人教训转化为系统改进，才是 Staff Engineer 思维。

Key Takeaways

  1. Bad news 越早说越好，掩盖问题是职业生涯的慢性毒药
  2. 带着方案，不只是问题：Problem + Options + Recommendation
  3. 量化影响：不要说"可能有问题"，要说"预计影响 X 用户/Y 笔交易"
  4. 决策后执行，不抱怨：你可以 disagree，但要 commit
