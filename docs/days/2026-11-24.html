🏗️ 系统设计 / System Design — Day 156 (Synthesis)

一致性模型全景图 — 从 Eventual 到 Linearizable 的工程决策

Consistency Model Panorama — Engineering Choices from Eventual to Linearizable

综合回顾: Day 12 (CAP), Day 9 (Replication), Day 39 (Cache), Day 47 (Consensus), Day 54 (Multi-Region)

🔍 为什么这很重要 / Why This Matters

过去60天，我们设计了YouTube、Google Maps、支付系统、分布式缓存……每次都会面临同一个问题：这个数据需要多强的一致性？ 今天把这些散落的知识串成一张决策地图。

Over 60 designs, one question kept recurring: how consistent does this data need to be? Today we unify the scattered lessons into a single decision framework.

⚡ 决策框架 / Decision Framework

问题1: 写后必须立即读到自己写的数据？ YES → Read-your-writes (session affinity / read-after-write) NO → 继续 问题2: 多用户并发写同一条记录？(如库存、余额) YES → Linearizable (单 leader + MVCC / distributed lock) NO → 继续 问题3: 数据有因果依赖？(评论早于回复) YES → Causal consistency (vector clocks / Lamport timestamps) NO → Eventual consistency is fine

🔴 别踩这个坑 / Common Mistakes

坑1: 把"高可用"和"强一致"当成对立面

实际上只是 latency vs consistency 的权衡。Redis Cluster 可以用 WAIT 实现 read-after-write，代价是 p99 延迟上升。

坑2: 对所有数据用同一策略

电商系统：商品价格用 Eventual（CDN 缓存），下单用 Linearizable（库存扣减），订单历史用 Read-your-writes（刚付完款要立刻看到）。

坑3: 忽略 clock skew

多 region 写时绝对不能用本地时间戳排序。用 Hybrid Logical Clocks (HLC) 或 Google TrueTime。

🧒 ELI5

就像餐厅记账：

  • Eventual：服务员先用便利贴记，晚点再录入电脑。可能短暂不同步，但最终一致。
  • Linearizable：收银机直接记，所有人看到的账都一样，但收银机坏了就完了。
  • Read-your-writes：你点的菜服务员一定记住了，哪怕其他人还不知道。

💻 算法 / Algorithms — Day 156

#312 Burst Balloons — Hard — 2-D Dynamic Programming (10/11)

🧩 二维DP模式 (10/11) — 在 Day 100 的模版基础上演进

本题是 2-D DP 系列最难也最经典的"区间 DP"变体。与前九题不同，它不是填充矩形网格，而是在区间上定义子问题。

🔗 Links

  • 🔗 LeetCode: https://leetcode.com/problems/burst-balloons/ 🔴 Hard
  • 📹 NeetCode: https://www.youtube.com/watch?v=VFskby7lUbw

🌍 真实类比 / Real-World Analogy

想象你在拆除一排建筑物，每拆一栋获得奖励 = 左邻 × 自己 × 右邻的价值。关键决策：你选择最后拆哪一栋。

This is like demolishing buildings where reward = left × current × right. The key insight: think about which building you demolish last in a range, not first.

💡 为什么这题难 / Why This Is Hard

直觉（错误）：每次戳价值最高的气球 → 贪心，WA。

正确思路：逆向思维。与其想"先戳哪个"，想"这个区间最后戳哪个"。

当气球 k 是区间 [i, j] 中最后一个被戳的，它两侧的气球已经全消失了，所以收益是固定的：nums[i-1] nums[k] nums[j+1]。

区间 DP 状态定义：
dp[i][j] = 戳爆区间 (i, j) 内所有气球的最大硬币数
           注意：i 和 j 本身是边界，不会被戳

转移方程：
for k in range(i+1, j):        # k 是这个区间最后被戳的
    coins = nums[i]*nums[k]*nums[j]  # k左右都已清空，邻居是i和j
    dp[i][j] = max(dp[i][j], dp[i][k] + coins + dp[k][j])

初始化：
nums = [1] + nums + [1]        # 两端加哨兵
dp = [[0]*(n+2) for _ in range(n+2)]

🐍 Python Solution with Trace

def maxCoins(nums: list[int]) -> int:
    # Add sentinel balloons at both ends
    nums = [1] + nums + [1]
    n = len(nums)
    dp = [[0] * n for _ in range(n)]

    # Enumerate by interval length (bottom-up)
    # l = length of open interval (i, j), so at least 2 apart
    for length in range(2, n):        # interval gap
        for left in range(0, n - length):
            right = left + length
            # Try each k as the LAST balloon popped in (left, right)
            for k in range(left + 1, right):
                coins = nums[left] * nums[k] * nums[right]
                dp[left][right] = max(
                    dp[left][right],
                    dp[left][k] + coins + dp[k][right]
                )

    return dp[0][n - 1]  # full range with sentinels


# Trace: nums = [3, 1, 5, 8]
# After padding: [1, 3, 1, 5, 8, 1]
# dp[0][5] = answer = 167

复杂度 Complexity:

  • Time: O(n³) — 三重循环
  • Space: O(n²) — DP 表

核心差异：Burst Balloons 用"枚举最后一个元素"代替"枚举相邻子结构"，是区间 DP 的精髓。

🧒 ELI5

拆积木游戏：你有一排积木，每次拆一块得分 = 左邻 × 自己 × 右邻。

技巧：不要想"先拆哪块"，要想"这一段最后留哪块"——因为只有最后那块的邻居是固定的！

🗣️ 软技能 / Soft Skills — Day 156 (Synthesis)

高级场景: 你被要求接手一个技术债务严重的核心系统

Senior Scenario: Taking Ownership of a Critical System Drowning in Tech Debt

综合主题: Day 16 (技术债务), Day 56 (快速上手陌生代码库), Day 51 (迁移/废弃), Day 32 (技术决策推动)

🎯 场景 / The Scenario

你新加入一个团队，第一周就被告知：你需要负责公司最核心的订单处理服务。这个服务已经7年没有重大重构，测试覆盖率 12%，P0 故障平均每月一次。你的老板说："我知道这很难，但我们需要你让它稳下来，同时不能停止新功能交付。"

You join a team and within your first week, you're handed ownership of the company's most critical order processing service. 7 years of accumulated debt, 12% test coverage, one P0 per month. Your manager says: "I know it's messy, but we need stability without stopping feature delivery."

🌟 STAR 拆解 / STAR Framework

Situation:

接手时：5000行无文档 Python 代码，依赖注入靠全局变量，DB 查询散落在业务逻辑里，无任何 metrics。

Task:

目标：6个月内把 P0 频率降到每季度一次，同时不延误产品 roadmap。

Action (分阶段策略):

第1-2周: 观察，不动 (Observe, Don't Touch) ├── 读代码，画出数据流图（不改代码） ├── 在 staging 跑所有已有测试，记录 flaky 的 └── 读最近3个月的 incident post-mortems 第3-4周: 插装，不重构 (Instrument, Don't Refactor) ├── 加 structured logging（不改逻辑） ├── 加 Datadog APM traces 到每个 DB 调用 └── 建立基线：p99 latency、error rate、call graph 第5-8周: 外科手术式修复 (Surgical Fixes) ├── 找出导致50%故障的根因（通常只有2-3个） ├── 只改高风险代码，每改一块先写测试 └── Code freeze: 新功能走 feature flag，旧路径不动 第9-24周: 渐进重构 (Strangler Fig Pattern) ├── 新逻辑写在新模块，旧代码调用新模块 ├── 每个 sprint 至少一个"测试覆盖率提升"任务 └── 每季度给上级一个覆盖率/稳定性报告

Result:

4个月后，P0 降至每季度1次；测试覆盖率从12%→41%；没有延误任何 roadmap 里程碑。

❌ vs ✅

❌ 新人常犯 / Junior Mistake✅ Senior 做法
"这代码太烂了，我要重写"先理解，再重构；Big Bang 重写风险极高
第一周就提大量 PR 改代码风格先建立信任，再推变化
把技术债务当纯技术问题量化业务影响（每次 P0 损失多少 GMV）才能说服上级投资
一次性重构所有问题Strangler Fig：新旧并行，渐进迁移

💡 Senior/Staff 加分点

  1. 用业务语言谈技术债："每次 P0 我们损失约 $X 收入 + $Y 工程师时间" > "代码质量很差"
  2. 主动建立 service reliability 目标，不等上级指派 SLO
  3. 把改善过程做成可见的：weekly tech debt burn-down chart 发给 stakeholders

🧒 ELI5

就像接手一套老房子：别第一天就砸墙。先住几周，找出哪里漏水、哪里电路有问题，然后先修最危险的，再慢慢翻新，整个过程不影响你住人。
