从单机到亿级：系统扩展的三阶段演进框架

Three-Phase Scale-Out Playbook: From Single Server to Billions

综合回顾 / Synthesis: 我们已覆盖 60 个系统设计主题。今天做一次大整合——把所有内容串成一个实战框架。
We've covered 60 system design topics. Today we stitch them into one cohesive decision framework.

想象你在设计一家创业公司的后端...

你的产品从 0 到 1 再到 1 亿用户。每个阶段的"正确答案"截然不同。

Your product goes from 0 to 100M users. The "right answer" changes completely at each stage.

🔑 每阶段的关键决策 / Key Decisions Per Stage

阶段 1 — 单体优先 (Monolith First)

  • 部署一个进程，Postgres 够用。Move fast. 不要过度设计。
  • 何时引入缓存？ 数据库 CPU > 70% 或 P99 延迟 > 100ms。
  • 教训：URL Shortener (Day 19)、Key-Value Store (Day 21) 都从这里开始。

阶段 2 — 第一次分布式 (First Distribution)

引入顺序：**缓存 → 读副本 → 消息队列 → CDN**（按 ROI 排序）

阶段 3 — 真正分布式 (Full Distribution)

  • Microservices：只拆分真正需要独立扩展的服务（别为了拆而拆）
  • 数据库：先分库分表（Sharding, Day 9），NoSQL 用于高写吞吐
  • 全局：Consistent Hashing (Day 11) + CAP 理论 (Day 12) 是核心武器
  • 跨区域：Multi-Region Active-Active (Day 54) 需要最终一致性设计

⚡ 为什么这样设计？核心权衡

过早微服务化是最常见的错误：

  • ✅ 微服务优势：独立部署、独立扩展、技术多样性
  • ❌ 微服务代价：网络延迟、分布式事务、运维复杂度 (Day 14)
  • 🎯 规则：单体 → 服务化，当团队 > 10 人或流量差异 > 10x

一致性 vs 可用性（CAP）的实战选择：

  • 支付系统 (Day 38) → CP（宁可拒绝也不能双扣款）
  • 推荐系统 (Day 46) → AP（短暂的数据不一致无所谓）
  • 聊天系统 (Day 28) → AP + 最终一致（消息送达比绝对顺序重要）

💻 算法 / Algorithms — Day 139

#300 Longest Increasing Subsequence (Medium) 🟡

🧩 一维动态规划 (11/12) — building on the template from earlier in this block

🧩 1-D DP (11/12) — 这是本模式倒数第二题。LIS 是 DP 的经典，也是面试高频题。
Second-to-last in the 1-D DP block. LIS is a DP classic and a high-frequency interview problem.

🔗 LeetCode #300 🟡 Medium

📹 NeetCode Video

🌍 真实场景 / Real-world Analogy

想象你在做一个股票分析工具，需要找出「价格序列中最长的持续上涨片段」（不要求连续）。

You're building a stock analyzer to find the longest sequence of strictly increasing prices (non-contiguous).

[10, 9, 2, 5, 3, 7, 101, 18] → 最长上升子序列长度 = 4 ([2, 3, 7, 101])

📐 映射到模版 / Template Mapping

本题的关键：dp[i] = 以 nums[i] 结尾的最长上升子序列长度

dp = [0] * (n + 1) # 标准模版 dp[0] = BASE_CASE # → dp[i] = 1 (每个元素自身是长度1的子序列) for i in range(1, n + 1): dp[i] = TRANSITION(...) # → max(dp[j] + 1) for all j < i where nums[j] < nums[i]

与前面题目对比：

  • Coin Change (Day 136): dp[i] = min(dp[i - coin] + 1) — 外循环是金额，内循环是硬币
  • Word Break (Day 138): dp[i] = any(dp[i-len(w)] and s[i-len(w):i] == w) — 外循环是位置，内循环是单词
  • LIS (今天): dp[i] = max(dp[j] + 1 for j < i if nums[j] < nums[i]) — 双重循环，两两比较

🐍 Python 解法 + Trace

from typing import List

def lengthOfLIS(nums: List[int]) -> int:
    n = len(nums)
    # dp[i] = length of LIS ending at index i
    dp = [1] * n  # base case: every element alone is length 1
    
    for i in range(1, n):
        for j in range(i):
            if nums[j] < nums[i]:
                # can extend the subsequence ending at j
                dp[i] = max(dp[i], dp[j] + 1)
    
    return max(dp)

# Trace: nums = [10, 9, 2, 5, 3, 7, 101, 18]
# i=0: dp = [1, 1, 1, 1, 1, 1, 1, 1]
# i=3 (nums[3]=5): j=2 (nums[2]=2 < 5) → dp[3] = dp[2]+1 = 2
# i=5 (nums[5]=7): j=3 (5<7) dp[3]=2 → dp[5]=3; j=2 (2<7) dp[2]=1 → dp[5]=max(3,2)=3
# i=6 (nums[6]=101): max over all j → dp[6] = 4
# Result: max([1,1,1,2,2,3,4,4]) = 4 ✓

时间复杂度 / Complexity: O(n²) time, O(n) space

⚡ 进阶：O(n log n) — 二分搜索优化

import bisect

def lengthOfLIS_optimized(nums: List[int]) -> int:
    # tails[i] = smallest tail element for all increasing subsequences of length i+1
    tails = []
    
    for num in nums:
        pos = bisect.bisect_left(tails, num)  # find insertion position
        if pos == len(tails):
            tails.append(num)   # extend the longest subsequence
        else:
            tails[pos] = num    # replace to keep tails as small as possible
    
    return len(tails)

# Key insight: tails is always sorted, but does NOT store the actual subsequence!
# tails = [2, 3, 7, 18] at the end, length = 4
# The actual LIS could be [2, 3, 7, 18] or [2, 3, 7, 101]

时间复杂度 / Complexity: O(n log n) time, O(n) space

举一反三 / Pattern Connections

本 1-D DP 块（12题）的规律总结：

题目dp[i] 含义转移方向
Climbing Stairs到第i步的方法数dp[i-1] + dp[i-2]
Coin Change凑成 i 元的最少硬币min over coins
LIS以i结尾的最长上升子序列max over j < i
Partition Subset (明天)能否凑成 ior over nums

共同点： 定义好 dp[i] 的含义，找到「如何从更小的子问题转移过来」。

🧒 ELI5

你有一排数字，想找最长的一组数，每个都比前一个大（不用挨着）。DP 的做法：对每个数，问「前面有哪些更小的数，它后面接上我能更长？」

You have a row of numbers and want the longest group where each is bigger than the last (not necessarily adjacent). DP says: for each number, ask "which earlier smaller numbers, if I follow them, make the longest chain?"

🗣️ 软技能 / Soft Skills — Day 139 (Synthesis)

从个人贡献者到技术领导：Staff+ 的思维升级

From IC to Tech Lead: The Staff+ Mindset Shift

综合题 / Synthesis Question:
"Walk me through how your definition of 'impact' has evolved over your engineering career. What does high-leverage work look like at your current level?"
「聊聊你对「影响力」的理解是如何随职业发展变化的。在你现在的级别，什么是高杠杆的工作？」

为什么这个问题很重要 / Why This Matters

这是 Staff+ 面试的核心问题之一。面试官在评估：

  • 你的视野是否超越了个人产出
  • 你是否理解组织目标和技术的连接
  • 你是否能 multiply 别人的效率

This is a core Staff+ interview question. The interviewer evaluates:

  • Whether your view extends beyond personal output
  • Whether you connect org goals to technical decisions
  • Whether you can multiply others' effectiveness

⭐ STAR 拆解

Situation: "Earlier in my career as a senior engineer, impact meant shipping features — velocity, code quality, uptime. I measured myself by what I personally built."

Task: "As I moved toward Staff, I kept seeing projects succeed technically but fail to move business metrics. I realized I was optimizing for the wrong thing."

Action: 三个具体转变 / Three concrete shifts:

  1. 从执行者到放大器 / Executor → Multiplier — 开始做代码审查培训、架构决策文档（ADR），让整个团队的工程质量提升，而不是只有自己写好代码
  2. 从问题解决者到问题定义者 / Problem Solver → Problem Definer — 在 PM 写需求之前，主动问「我们真正想解决的用户痛点是什么？」——避免了两次大型功能的重做
  3. 从技术优先到影响优先 / Tech-first → Impact-first — 学会说「这个技术很酷，但对 OKR 没有直接贡献，我们先做 X」

Result: "The team's shipping velocity actually increased 30% after I stopped trying to do everything myself. More importantly, I could point to 2 projects where early architecture input prevented months of rework."

❌ Bad vs ✅ Good

❌ 避免这样回答： "I've always cared about quality and impact." (空话，无具体例子)

✅ 更好的结构： 给出一个明确的「认知转折点」——具体是哪件事让你意识到需要改变思路，改变后发生了什么。

🎯 Senior vs Staff vs Principal 的影响力差异

Senior: My code/feature → team's codebase Staff: My decisions/docs → multiple teams' velocity Principal: My org's architecture → company's roadmap

面试中被问到「高杠杆工作」，Staff 级别的答案应该包含：

  • 技术系统 (不只是代码，还有文档、ADR、工具链)
  • 人的系统 (培养，招聘，onboarding)
  • 流程系统 (减少重复决策，建立护栏而不是规则)

🔑 Key Takeaways

  1. 高杠杆 = 力量倍增器。 花 5 小时写一篇好的架构文档，能节省团队 50 小时的反复讨论。
  2. 推动 > 执行。 Staff+ 的核心是找到正确的问题，而不是更快地解决错误的问题。
  3. 沉默的影响力也要说出来。 你阻止了一个坏决策，也是贡献——要学会量化和表达"avoided impact"。

🧒 ELI5

初级工程师就像一个好厨师——做好每道菜。Staff 工程师就像主厨——不一定亲手做每道菜，但负责整个厨房出品的质量和速度。

A junior engineer is like a great cook — makes each dish well. A Staff engineer is like a head chef — doesn't personally cook everything, but is responsible for the whole kitchen's output quality and speed.
